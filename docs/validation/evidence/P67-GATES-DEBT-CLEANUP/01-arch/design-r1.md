## 1. #1 四案对比与关键技术张力判定

| 维度 | A：条目上限到 N 拒写 | B：LRU 淘汰 | C：TTL+上限 | D：LRU+TTL |
|---|---|---|---|---|
| 实现复杂度 | 低 | 中 | 中 | 高 |
| 失效语义正确性 | 正确但**缓存停滞**（新 sha 永远 miss） | 正确（淘汰=失去命中机会，永不错误命中） | 正确 | 正确 |
| 空间上界 | 硬 N | 硬 N | 软（依赖过期检查时机） | 硬 N+TTL 兜底 |
| 对现有 96 条 | N≥96 不清理、之后拒写 | put 后逐条淘汰最旧 mtime | 到期逐步清 | 同 B |
| 风险 | 中：缓存退化为死缓存 | 低 | 中：需时间源+时机语义 | 低 |
| 推荐度 | 低 | **推荐** | 中 | 不必要 |

**关键张力独立判定（mtime 访问序）**：LRU 需要访问序，而值结构 `{v:2, corpus}` 不得加时间戳。候选做法——以条目文件 mtime 为访问序（put 写入、get 命中 touch、超限删最旧 mtime）——逐条对照 3.1.2 边界：

- **值结构未变** ✅：mtime 是文件系统元数据，不在 JSON 值内；`validValue`（g4b.js「A stored value must be exactly `{v: 2, corpus: string[]}`」）不变。
- **键五分量未变** ✅：`keyString` 五分量（`CACHE_VERSION|resolved sha|scope kind|whitelist source|whitelist text digest|source digest`）与 `fullKey` 不动。
- **命中=与冷跑等价** ✅：命中分支仍 `corpus = new Set(stored.corpus)`；touch 仅改 mtime，不改语料。
- **fail-open 保留** ✅：touch/枚举/unlink 任一失败静默忽略，命中与淘汰均不改变 verdict 语义；极端情形（淘汰竞态漏删）只让条目数瞬时超过 N，绝不产生错误命中。
- **只存语料不存结论** ✅：mtime 不承载结论。

**跨进程竞争容忍**：多进程并发读删下，unlink 已在另一进程持读句柄时于 Windows 上会失败（静默跳过，条目存活）；两进程同时淘汰可能多删（最坏条目数略低于 N，无害）；同时 put 不同 key 各自淘汰亦无害。全部路径 fail-open。
**判定**：LRU（案 B）在边界内可落地。**建议 N=100**（覆盖现状 96 条、留 4 条余量；旧 sha 条目永不再命中——`resolvedSha` 取 HEAD/baseRef，前进后旧条目自然失效——故淘汰最旧 mtime 即淘汰纯占位条目，TTL 冗余，案 C/D 不必要）。
