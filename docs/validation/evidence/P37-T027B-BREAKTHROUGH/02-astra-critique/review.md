【批注】批判主旨：第 1 轮列出了安全目标，却未闭合“启动所有权→证据持久化→费用提交→核心接受”的交接。
【推断】最致命之一：spawn 后失败仍可能落入“未启动”错误支路，回收失败又释放所有权，留下不可寻址进程（C2）。
【推断】最致命之二：完成记录耐久不代表其引用的证据原件耐久，重启后可能只剩“完整”的收据（C4）。
【推断】最致命之三：G1 隐含本轮边界之外的生产解锁前置，G2 又提前需要真实调用，原门序不能直接作为 11 月实施承诺（C7）。

**C1 死锁与锁序**
【事实】设计仅称“run 单写所有权常驻”“固定锁序”；[process.go:237](internal/guard/process.go#L237) 却在建立有界验证 context 前直接调用 `Process.Wait()`；[engine.go:218](internal/chain/engine.go#L218) 同步等待 reviewer。
【推断】停机失败且进程不退出时，外层超时不能解除等待；若新装配用 run 互斥锁包住整个执行，评审响应又经同锁控制 API 返回，便形成自锁。这是可构造路径，不是已实测死锁。
【批注】最小修法：区分常驻所有权与短期互斥；禁止跨等待持业务锁，禁止端口同步反调核心；底层等待必须有截止出口。

**C2 孤儿进程**
【事实】[agent_runner_launcher.go:8](internal/chain/agent_runner_launcher.go#L8) 规定 error 意味从未 spawn；启动器身份镜像失败后却停止并返回 error，[agent_runner_pinned_cli.go:197](internal/adapters/agent_runner_pinned_cli.go#L197)；其停止入口无论成功与否均释放 launch。
【推断】身份发布失败叠加停机未证时，dispatcher 无法从返回值取得受管对象；释放槽位又可能允许另一请求进入。已有 Job 挂起创建不能消除此交接缺口。
【批注】最小修法：spawn 即登记所有者；失败结果必须携带可定位的内部受管对象，不能冒充未启动；未证空树不得释放执行窗口。

**C3 TOCTOU**
【事实】[agent_runner_evidence.go:420](internal/adapters/agent_runner_evidence.go#L420) 检查已开句柄大小，随后却按路径重新读取；[process_windows.go:176](internal/guard/process_windows.go#L176) 在身份检查后另按 PID 执行 taskkill。
【推断】检查后替换文件可绕过大小与对象绑定；旧进程退出后 PID 重用，可使停止动作指向另一进程。“每次发布复检”挡不住复检之后的替换。
【批注】最小修法：限长读取、哈希和对象身份检查使用同一句柄；既有 guard 停止实现保持经验证对象的连续引用。目录 ACL、候选安装区保护与残余窗口分别举证，不能统称已消除。

**C4 状态机漏洞**
【事实】G1 列举 R、launch、完整 terminal 载荷；[agent_runner_evidence.go:439](internal/adapters/agent_runner_evidence.go#L439) 的工件写入只有临时文件、Close、Rename，没有同步屏障。
【推断】即使以后某 Windows/P 的记录发布获证，断电仍可能留下 completed C、丢失日志或 manifest。摘要存在并不能重建原件；下游可能正确拒绝，但已无法兑现“证据完整”。终局槽只能拒绝异终局，不能修复这个缺口。
【批注】最小修法：terminal-intent 前验证证据引用闭包已持久化；缺失、未知停机或采集未收敛不得产生 completed。任何线程都不能另造一份终局覆盖赢家。

**C5 幂等与重放**
【事实】设计要求 Wait 重入只读；现[agent_runner_postflight.go:695](internal/adapters/agent_runner_postflight.go#L695) 会使用当前时间构造完成体；[engine.go:183](internal/chain/engine.go#L183) 重入任务时仍调用 Materialize，待评审态却不重跑已认证 postflight。
【推断】重复采集会改变完成摘要并冲突；若新 Materialize 每次从父快照重建，便可能让旧门禁资格覆盖新内容。跨任务复用单请求端口也不能靠相同方法签名保证正确。
【批注】最小修法：同请求只运行一个等待者；已有意图只从意图恢复；物化必须状态感知，冻结候选须与原事实按内容对账。缺任务绑定拒绝，resume 不猜测。

**C6 计量与预算**
【事实】[cost.go:514](internal/tickets/cost.go#L514) 的 Settle 只更新内存；[cli.go:499](internal/console/cli.go#L499) 加载账本后调用装配，没有结算落盘屏障。设计仍拟复用接受具体 `*CostLedger` 的 publisher。
【推断】新装配若直接照搬，两进程可从相同余额分别预留；R 已发布而新预留未持久化时崩溃，跨 run 将低估占用。结算内存成功也不能证明 C 发布前已持久入账。
【批注】最小修法：引入持久预算适配端口，短事务内重读、校验、提交并返回持久确认；unknown 持续占用，保留现有结算键。真实迭代的调用上限还须启动前可强制，不能只事后计数。

**C7 门序与可行性**
【事实】[CONTRACTS.md:210](docs/CONTRACTS.md#L210) 明定平台升级须协议先行；本轮禁止改变契约语义。设计 G2 已要求官方会话正例，真实调用授权却在 G4 再列；十项必验能力还包含 sessionResume。
【推断】G1 不能仅凭补证自动解锁；若等 G4 才获调用授权，G2 无法执行。先完成全部耐久工程再验证候选能否在边界内工作，还可能把大笔投入放在死路之前。
【批注】最小修法：G0 明列这些外部前置；区分机制开发门与生产解锁门，提前安排获授权的同边界可行性探针。未满足前置保持阻塞，不以月份替代条件。

**R1 最小重构**
以下均为【批注】，只调整内部接口与执法，不新增 wire 状态，不改变既有迁移和结算顺序。

1. **C1**：run 所有者串行提交状态；预算锁与 replay 锁不嵌套，回调不持锁、不反调。等待到界返回不确定，但不能顺便释放仍存活写者的所有权。
2. **C2**：将 Prepare 结果变为不可复用的受管资源对象，绑定请求、边界与运行上限。Job、权限及回收责任就绪后才恢复执行；身份发布失败继续由原所有者负责。
3. **C3**：路径字符串仅用于定位，安全决定绑定打开对象；候选配置、文件读取及停止动作不得在校验后重新按名字选择对象。
4. **C4**：增加内部证据提交屏障，覆盖日志、usage、manifest/diff、停机与 pid 原件；成功后才进入既有 intent→结算→C→closure。
