## 3. 组合装配设计（console 侧）

### 3.1 装配入口与构造顺序（`ExecuteAgentRunnerRun`）

输入 `AgentRunnerAssemblyOptions`：`RunID`、`RunRoot`、`Definition`（经 `cfg.ToDefinition()`）、`RequestRecord`、`CapabilityRecord`、`EnforcementRecord *`（可 nil，nil 即进入 §5 拒绝）、`AvailabilityRecord` + `AvailabilityPolicy`、`AuthorizationLedger`、`CostLedger`、`AgentCLI{Executable, Version, VersionArgs, Grace, Timeout, VerifyWait, MaxLogBytes}`、`Clock`、`IDs`。

构造顺序（每一步失败即 fail-closed 返回，不留半成品）：

1. **装配前置拒绝**（§5 编号 1/8）：definition 必须恰好含一个 isolated-workspace `code` 步（多步/多任务/hook 步 ⇒ 拒绝）；所有记录字段非空且可解码/可验证（用既有 `Validate*` / `Decode*`）。**零新哨兵**：前置拒绝复用既有 `console.ErrInvalidConfig`（包裹缺项名）——v1 曾写新哨兵名 `ErrAgentRunnerAssemblyIncomplete`，已被用户硬约束（零新哨兵、不上 wire、不进 `error.schema.json`）取代（见整改记录 r2 的 N2）。
2. **run root 标记先行**：`MkdirAll(runRoot/events)` + 空 `state-events.jsonl`（不存在才建；resume 复用既有）——顺序铁律：标记必须先于 replay store 构造（`NewAgentRunnerReplayStoreForRun` 校验标记存在，A0 契约）。
3. `store := adapters.NewAgentRunnerReplayStoreForRun(runRoot, runID)`（自建 `agent-runner-replay/{requests,completions,launches,terminals,runs}`）。
4. `store.RejectWriterRoots(workspaceRoot)`（workspace 与 replay root 双向不相交；A0 纪律）。
5. `snapshotStore := snapshot.NewStore(runRoot/snapshot-store, 0)`；workspace root = `runRoot/workspaces/<task>-attempt-1`（Materialize 端口物化）；`capturer, err := NewAgentRunnerSnapshotCapturer(snapshotStore, runID, taskID, 1)`（pre-manifest wrapper 与 (A′) 采集共用捕捉口径，§3.5；同根两个 store 实例按 hash 寻址写对象、幂等无冲突）。
6. `launcher := NewAgentRunnerPinnedCLILauncher(config, store)`（钉版校验；子进程由 `guard.RunManaged` 启动，launcher 注入 `PROOFRAIL_EVIDENCE_DIR=<store>/runs/<requestId>`）。
7. `dispatcher := AgentRunnerReplayDispatcher{Store, Launcher, Process, LedgerSnapshot: func() {return AuthorizationLedger}, CostLedger, RequestRecord, Clock}`。
8. `admission := AgentRunnerCompositeAdmission{...}`（EnforcementRecord 可为 nil）。
9. `intents := NewAgentRunnerStepIntentPreparer(RequestRecord, definition)`。
10. `postflightPort := NewAgentRunnerPostflight(store, RequestRecord, snapshotStoreRoot, ...)`（实例绑定 request record ⇒ requestID，§4）。
11. `publisher := AgentRunnerTerminalPublisher{Store, CostLedger, RequestRecord, Clock}`。
12. `runtime := &agentRunnerRuntime{...}`（七端口：Baselines=workspace 条目摘要、Workspaces=Materialize、Steps=`chain.StepRouter{AgentRunner: &preManifestAgentRunnerPort{inner: dispatcher, capturer: capturer}, AgentRunnerAdmission: admission}`（wrapper 在 dispatch 前捕捉 pre-manifest 并存入 `runtime.beforeManifest`；捕捉失败置 nil 仍派发——与 `Run` 的「capture gap 降级而非中止」同语义，§3.5）、Acceptance=真实 snapshot candidate 冻结、Reviewer=策略 approve 带证据摘要、Publisher=promotion（重验 workspace 摘要 + 无存活受管进程）、Stopper=声明 launcher 拥有停机、Reconciler=只读核对）；`runtime.waitRun = &adapters.AgentRunnerPinnedCLIRun{Launcher: launcher, Store: store, Clock: clock}`（(A′) 入口载体；**必须与 dispatcher 共用同一 launcher/store 实例**，否则 registry handle 与证据目录无法解析到已派发的 run，§3.5）。
13. `engine := chain.New(Options{..., Postflight: postflightPort, ...})`。

### 3.2 驱动循环（与 B4 harness 同构，但全走生产路径）

1. `engine.Run(ctx)` ⇒ 期望 `ErrAwaitingAgentRunnerTerminal`。
   - **Windows**：`RecordRequest` 先拒（durability unproven）⇒ dispatcher 返回 `ErrAgentRunnerReplayStoreDurabilityUnproven`（错误链）⇒ engine 写 step/task FAILED ⇒ 装配返回该错误。**这就是 Windows 上生产派发的真实终局**（§5 编号 7，拒绝腿）。
   - **Unix**：R 已发布 ⇒ step `TERMINAL_PENDING`。
2. 等待/采集/映射：`runtime.waitRun.WaitAgentRunnerDispatched(ctx, agentRunnerRunRequest, runtime.beforeManifest)`——(A′) 入口（§3.5）：不 spawn、不写 R/intent/identity、不触 chain 状态；看门狗、guard 停机、五枚冻结事实与 `Run` 同序，仅去掉 spawn 与其专属前置。`agentRunnerRunRequest` 的 Launch 字段与 dispatcher **同源构造**（同一 `AgentRunnerProcessConfig`、同一 workspace root，§3.5.1）。
3. 终局发布：`publisher.PublishTerminal(ctx, outcome)`（intent → 账本 `Settle` → C → closure，A3 四阶段）。
4. 路由：`terminal, _ := ToChainAgentRunnerTerminal(request, intent, closure)`（或 `LoadChainAgentRunnerTerminal`）→ `engine.SubmitAgentRunnerTerminal(ctx, terminal)` ⇒ completed 路由 step `PASSED`。
5. `engine.Run(ctx)` 再入 ⇒ 走完 postflight → `REVIEW_PENDING` → freeze → review → promotion ⇒ task `PASSED`、chain `COMPLETED`。
6. 非 completed 终局（failed/cancelled/uncertain/operator）按 A4 路由后停止；本片只对 completed 与「拒绝」两类腿取证。

### 3.3 run root 与 `runs/`、`PROOFRAIL_*`

- run root：沿用 CLI 既有口径（`--run-dir` 或 `<chainDir>/tmp/prfrail-runs/<runID>`）；**不新增** `PROOFRAIL_*` 环境变量。
- `runs/`：即 `<runRoot>/agent-runner-replay/runs/<requestId>/`，A6 冻结证据目录，launcher 以既有常量 `PROOFRAIL_EVIDENCE_DIR` 注入子进程；装配不发明新 env 语义，`AgentCLI.Env` 仅作透传。

### 3.4 `ExecuteNoopRun` 保持不变

`ExecuteNoopRun` 函数文本逐字不变；`localRuntime`（含 fail-closed postflight）整体移入 `runtime_noop.go` 后语义不变（同包）。noop 链不可能到达 postflight（无 AgentRunner 终局可路由），故该 fail-closed 桩在 noop 路径上契约正确、予以保留并文档化——J-a2 的 grep 判据据此成立（`runtime.go` 不再含桩，桩只在 noop 专用文件）。

**缘起**：§3.2-2 与 §6 v1 曾假设 dispatcher 派发后调 `AgentRunnerPinnedCLIRun.Run` 做等待/采集/映射。②b 实测不可实现：`Run` 自己 spawn（`internal/adapters/agent_runner_run.go:56` 起，`:83-90` 一带经 `run.Launcher.StartAgentRunnerProcess`），与 dispatcher 共用「每 run root 单次 launch」锁（`agent_runner_pinned_cli.go:126` `ErrAgentRunnerProcessDuplicate`、`:128`/`:368` `ErrAgentRunnerLaunchConflict`）；且 `Run` 在生产代码**无任何调用者**（仅测试，§13）。`tools/b4-e2e/runmap.go:24-39` 权威注释同证并因此镜像重写 9 个未导出生产函数。用户裁定 **(A′)**：在 `internal/adapters/agent_runner_postflight.go`（与未导出助手同包）新增不 spawn 的「已派发后等待/采集/映射」导出入口，console 调它；**明确不取 (B′)**（console 镜像映射层）；认可 adapters 公开面 +1 导出函数，但入口必须最小，任何越界（如顺手加 launch 入口）即停下回 ①。

#### 3.5.1 签名与语义边界

```go
// WaitAgentRunnerDispatched waits for a run the dispatcher already started,
// collects its evidence and maps it into the terminal outcome. It is the
// post-dispatch half of the offline run and never starts a process, never
// writes replay-store records (no R, no intent, no identity) and never
// touches chain state: the caller owns terminal publication (§3.2-3).
// beforeManifest must be the workspace manifest captured before dispatch; a
// nil capture is a manifest gap that degrades the outcome exactly as
// AgentRunnerPinnedCLIRun.Run does - never a silent pass. Launcher and Store
// must be the same instances the dispatcher used, so the launch handle and
// the evidence directory resolve to the run that is already live.
func (run *AgentRunnerPinnedCLIRun) WaitAgentRunnerDispatched(ctx context.Context, request AgentRunnerRunRequest, beforeManifest []byte) (AgentRunnerTerminalOutcome, error)
```

（方法体落于 `internal/adapters/agent_runner_postflight.go`；方法与 `AgentRunnerPinnedCLIRun` 同包，`run.Launcher/Store/Clock` 即 §3.1-12 注入的同一批实例。）

语义边界（硬约束，② 与 ⑦ 必须逐条核验）：
1. **不 spawn**：全函数不调用 `StartAgentRunnerProcess`；`launchID` 由 `agentRunnerLaunchID(request.Launch.RequestID)` 重推（`agent_runner_replay_dispatcher.go:218`，未导出、同包可调），与 dispatcher 派发时同值。
2. **不写 R / intent / identity**：零 replay-store 写、零事件日志写；唯一状态读取 = `WaitAgentRunnerProcess` 所需的 registry handle 与 `RunEvidenceDir`。
3. **不触 chain 状态**：不构造/不调用 Engine；返回 `AgentRunnerTerminalOutcome` 由 caller（§3.2-3 的 publisher）终局化。
4. **校验与 `Run` 同批同序**：nil receiver/Launcher/Store、ctx、RequestHash、TaskID/StepID/Attempt、Timeout、MaxLogBytes——同一批 `ErrInvalidAgentRunnerRun` 前置；`Clock` 缺省同 `Run`。
5. **停机处置与 `Run` 同构**：`agentRunnerNeedsDurableStop` 为真 ⇒ `StopAgentRunnerProcess`（公共受审停机，natural exit 得 already-stopped 证明）；否则 ⇒ **同包直调 `run.Launcher.releaseLaunch(launchID)`**——正是 `Run` 的 default 分支，B4 harness 镜像差异 (a) 在此消除（§3.5.4 第二用例守护）。
6. **采集/树校验/映射全复用未导出助手**（清单见 §3.5.3）：`CollectAgentRunnerEvidence`（`BeforeManifest=beforeManifest`）→ `agentRunnerVerifyTreeGone` → `agentRunnerTerminalStatus` → `agentRunnerCompletionFor`/`agentRunnerSettlementFor` → completed 时 `FrozenFacts()`。`beforeManifest == nil` ⇒ collector 记 gap ⇒ 结局降级 uncertain（与 `Run` 的 capture-gap 语义一致，`agent_runner_run_test.go:689` 同判）。
7. **入口最小**：仅上述六步；不新增 launch 入口、不新增哨兵、不新增 DTO 字段。

#### 3.5.4 差异化测试设计（漂移护栏）

**一句话**：两个互不相关的 run root + 同一确定性 `tools/agent-stub` 二进制 + 同一 `AgentRunnerRunRequest`（同 requestID、同 flags）+ 同一固定 `Clock` 与同一 `AgentRunnerSnapshotCapturer` 捕捉口径——root A 走 `Run`（自 spawn），root B 先用 `StartAgentRunnerProcess`（dispatcher 同款公开启动端口）spawn 再走 `WaitAgentRunnerDispatched`（传 spawn 前同一工作区捕捉的 `beforeManifest`），断言两份 `AgentRunnerTerminalOutcome` 逐字段相同；物理上不可相同的字段用替代断言闭合。

| 字段（completed 结局） | 逐字段相同？ | 依据 / 替代断言 |
|---|---|---|
| `Completion` 的 Kind/CompletionID/RequestID/RequestHash/RunID/TaskID/StepID/Attempt/AdapterID/SessionID | ✅ 相同 | 全部由 request 派生 |
| `Completion.Status` / `ProcessTreeStatus` | ✅ 相同 | 同 stub 模式（`mutate-workspace` 自然退出 ⇒ completed/stopped） |
| `Completion.ExitCode` | ✅ 相同 | stub 退出码固定 |
| `Completion.Evidence` / `ErrorEvidence` | ✅ 相同 | 仅 RequestHash；completed 无 ErrorEvidence |
| `Completion.CompletedAt` | ✅ 相同 | 两路注入同一固定 `Clock` ⇒ 同值 |
| `Completion.OutputManifestHash` | ❌ 不同 | post manifest 字节含 `snapshot` 捕获时间戳 `CapturedAt`（`internal/snapshot/capture.go:275` 内部 `time.Now()`，不可注入）⇒ 替代断言：各自 = `Digest("", 本根 manifest.post.json 字节)`（自洽）；A/B 解码后 `Entries` 逐条目全等 |
| `Settlement` 全部字段 | ✅ 相同 | stub `usage.json` 完全确定性（固定 calls/tokens/duration-ms） |
| `Facts.DiffHash` | ✅ 相同 | diff 报告仅含条目（无时间戳） |
| `Facts.LogHash` | ✅ 相同 | 日志流 = 固定 marker 行，无 PID/时间 |
| `Facts.UsageHash` | ✅ 相同 | usage 确定性同上 |
| `Facts.ManifestHash` | ❌ 不同 | 根因同 `OutputManifestHash` ⇒ 替代断言同上 |
| `Facts.ProcessStopEvidenceHash` | ❌ 不同 | guard 停机证据 canonical 含 PID + StartToken + Requested/Verified 时间戳（`internal/guard/process.go:281` 摘要口径）⇒ 替代断言：A/B 各自解码证据前缀（域 `proofrail:termination-evidence:1`）且 `Outcome=="stopped"`、`Actions` 相同，仅 Identity/时间不同；两路停机分支一致（completed 腿均 natural-exit ⇒ 同一公共 `StopAgentRunnerProcess` 的 already-stopped 证明） |
| `Facts` 非 nil 且五枚两两互异 | ✅ 相同 | 共享 `FrozenFacts.Validate` |

**第二用例（guard 停机腿）**：stub `hang` + 短 Timeout ⇒ 两路均走 `default` 分支（guard 已停 ⇒ **同包直调 `releaseLaunch`**）；断言 A/B 的 `Status=="uncertain"`、`TreeStatus` 相同、`ErrorEvidence` 除停机摘要元素外逐项相同、且**两路 launch slot 均被释放**（同一 root 可再次 `StartAgentRunnerProcess` 不被 `ErrAgentRunnerLaunchConflict` 拒）——该用例专门证明 B4 harness 镜像差异 (a) 在生产同包入口中已消除。

**不可消除差异的声明**：上述三个 ❌ 字段在物理上不可能跨进程逐字节相同（时间与 PID 是真实系统的身份要素），故对它们以「自洽 + 结构等价」替代「逐字节相等」；其余 ✅ 字段必须逐字段相等，任一漂移即红。

## 4. 生产 `PostflightPort` 实现设计（`internal/adapters/agent_runner_postflight.go`）

- **文件职责注（v2）**：本文件按用户裁定同时承载 §3.5 的 (A′) 入口 `WaitAgentRunnerDispatched`（同包获得未导出助手；职责与 postflight 端口分离，二者无调用关系）。

- **形态**：`AgentRunnerPostflight` 为绑定式端口——`NewAgentRunnerPostflight(store *AgentRunnerReplayStore, request AgentRunnerRequestRecord, snapshotRoot string)`。`RunPostflight` 先校验 `request.RunID/TaskID` 与绑定记录一致，否则 fail-closed 返回（不改 `PostflightRequest` DTO、不新增接口；requestID 取自绑定记录）。
- **数据来源**：`store.RunEvidenceDir(request.RequestID)` 的 A6 冻结工件 `manifest.pre.json / manifest.post.json / diff.json / logs/{stdout,stderr}.log / usage.json / stub.pid / stub-child.pid` + `PostflightRequest.Workspace`。
- **五枚冻结事实的独立重推与逐项对账**（六腿，域前缀 `proofrail:agent-runner-postflight-leg-*:1`，不得用 b4 域）：
  1. `ManifestHash`（post manifest 工件摘要）：重新捕获 workspace（`internal/snapshot` 同一捕捉口径）⇒ 条目集与存储 post manifest **严格相等**（changed paths ⇒ failed，列出路径）。
  2. `DiffHash`：由存储 pre manifest 与新鲜捕获重算 diff ⇒ 字节级等于 `diff.json`（不等 ⇒ failed）。
  3. `LogHash`：重读两条日志流**原始字节**拼接摘要 == `Facts.LogHash`（A6 口径：不先解码）。
  4. `UsageHash`：重读 `usage.json` 摘要 == `Facts.UsageHash`。
  5. `ProcessStopEvidenceHash`：独立重验——对 `stub.pid`/`stub-child.pid` 报出的 pid 做 `guard.InspectProcess` + `ProcessAlive`，任一存活 ⇒ failed；全部消失 ⇒ 事实主张成立（hash 本身随 passed 证据携带，guard 停机证据字节不可由端口重建）。
  6. 范围/秘密/副作用：`gates.DefaultSecretScanner` 扫捕捉条目（普通文件）；文件类型/大小由 snapshot 捕捉口径承担。
- **failed / uncertain 语义**：任一腿「证明事实错误」⇒ `PostflightFailed`（ErrorEvidence = 域摘要 + 细节）；「无法证明」（工件不可读/捕捉失败）⇒ `PostflightUncertain`。引擎侧已冻结：failed ⇒ task `REPAIR_PENDING` + chain `PAUSED`；uncertain ⇒ task `FAILED` + chain `PAUSED` 禁重试。
- **不写状态**：端口只读 evidence 目录与 workspace；零写 replay store、零写事件日志、不触 Engine。passed 的 `Evidence` = 五枚事实摘要 + 六腿摘要（满足 A5「必须携带全部五枚事实摘要」）。
- **与 `tools/b4-e2e/postflight.go` 的差异与不可直接搬运理由**：package main；requestID 是硬编码 `"request-"+runID`；摘要域 `proofrail:b4-*`（与生产域混用会污染证据语义）；经 `p.owner` 写 harness journal（生产端口无此物）；无 request-record 绑定校验。可复用的是**对账算法与腿结构**，须重写载体（包、绑定、域前缀、journal 移除）。
- **继承边界（不改）**：snapshot 捕捉默认排除集（`.git/**`、`.prfrail/**`、`tmp/**`）的盲区（B4 偏差 3 实测）原样继承，本片不改排除集，仅如实文档化。

## 5. 拒绝路径设计（行为 + 错误哨兵 + 不 spawn 证明）

| 条件 | 行为 | 哨兵（`errors.Is` 可识别） |
|---|---|---|
| 1. 缺 capability / 请求记录 / 可用性记录（装配输入缺失或解码失败）；definition 不是「恰好一个 isolated code 步」 | 装配前置拒绝：engine 尚未构造 | **零新哨兵**：复用既有 `console.ErrInvalidConfig`（包裹缺项名）—— v1 曾写新哨兵 `ErrAgentRunnerAssemblyIncomplete`，已被用户硬约束取代（见整改记录 r2 的 N2 与 §3.1 步 1） |
| 2. 无 enforcement 记录（disposition != compatible） | admission 拒绝 | `ErrAgentRunnerCompositeAdmissionBlocked` ← `ErrAgentRunnerAdmissionBlocked`（reason `external enforcement required`） |
| 3. 缺可用性 / status != available / 通道或 profile 不匹配 / 预算超限 | admission 拒绝 | `ErrAIUnavailable`（reason 区分 stale/mismatch/budget） |
| 4. 记录过期（enforcement `probedAt` 早于 capability 或超 `MaximumAge` 或晚于评估时刻；availability 同理） | admission 拒绝 | 同上（`stale or future enforcement evidence`） |
| 5. 绑定不匹配（enforcement 与 capability/executable/config/platform 哈希；request 与 step/attempt/parent；authorization scope；budget reservation 绑定） | admission 拒绝 | `ErrAgentRunnerCompositeAdmissionBlocked` 下各 reason（`enforcement binding mismatch` / `step request or adapter candidate binding mismatch` / `authorization scope mismatch` / `cost reservation binding mismatch`） |
| 6. 平台不匹配（capability OS/Arch/PlatformHash ≠ 当前评估环境） | admission 拒绝（compatible 也不豁免平台校验，契约冻结） | `capability platform mismatch` |
| 7. Windows durability unproven | dispatcher `RecordRequest` 拒绝：R 未创建、无 intent、无 identity、**无 spawn** | `ErrAgentRunnerReplayStoreDurabilityUnproven` |
| 8. 反向腿「无记录 ⇒ 拒绝启动」 | 即编号 1/2/3：装配层或 admission 层拒绝，事件日志不出现 dispatch 三哈希证据 | 同上各哨兵 |

**不 spawn 证明（两层）**：
- 结构层：全仓唯一进程产出点 = `AgentRunnerPinnedCLILauncher.StartAgentRunnerProcess` → `guard.RunManaged`。`StepRouter.ExecuteAgentRunner` 顺序 = admission 先于 dispatch；dispatcher 顺序 = `RecordRequest` → launch reconfirm → intent → 才调用 launcher。编号 1–6 在 admission 内短路，编号 7 在 `RecordRequest` 短路 ⇒ 任何拒绝路径都到不了 launcher。
- 证据层：每条拒绝腿的测试断言——`<runRoot>/agent-runner-replay/runs/` 空、`launches/` 空、run root 无 `managed-process.identity.json` 镜像、事件日志 step 为 `FAILED` 且无 `agent-dispatched` 转移；由此机械证明零 spawn。

## 10. 风险与「仅静态推断、未实证」清单

**风险**：
1. postflight 对账写错 ⇒ 拒绝误判为通过（最高风险）；M4 + Codex 终审 + 必抽盲审守护。
2. 正向全链只能在 Unix 跑通，Windows 无生产正向腿（durability 平台常量，本片无法改）；若用户坚持 Windows 正向证据 ⇒ 需回 ① 或先做 durability 升级片（B3b/B3c 域，超出本片）。
3. 装配限「恰好一个 AgentRunner 步」；多步/多任务、hook 步、operator-action、取消、崩溃恢复均拒绝或未覆盖（未实证清单）。
4. CLI flags 若入本片，产品文档（INSTALLATION/OPERATIONS）可能出现滞后。

### r3 已知差异（用户要求逐字记录）
