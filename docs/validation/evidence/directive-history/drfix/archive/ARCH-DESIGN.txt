## 1. 结论：根因判定（含任务 A / B 的明确答案）

### 1.1 任务 A —— 交织证据归属判定（逐字）

**判定：DR-5 失败日志（run `35622599102`，head `b597728`）中 3 条 `AUDIT TRAIL BROKEN` 行，不是"共享 rig / 临时目录"的证据。** 三条各有独立归属，逐条如下：

**(a) 两条 `write … file already closed` 变体 —— 反向用例的**正常 fail-closed 输出（设计内行为）**。**

- 机制：`eventLogger.fail()` 在首次写失败时向 stderr 打印该行——`main.go:136-141`：
  > `fmt.Fprintf(os.Stderr, "enforcement-proxy: AUDIT TRAIL BROKEN (%v): requests are denied until the log is writable again\n", err)`
- `TestAuditTrailFailureDeniesRequests` 在 `main_test.go:87` 处 `logger.close()`（注释原文："the audit trail becomes unusable"）后发请求；此时 `logger.err()`（`main.go:143-148`）返回 `l.failure`，首次请求到来时 `failure` 仍为 nil，于是走到 pre-flight 写入（`handlePlainHTTP` 的 `p.logger.log`）→ `l.w.Write` 命中已关闭文件 → 报 `write …: file already closed` → 打 403，测试断言 403（`main_test.go:101`）。该告警串是**该测试存在的目的**。
- `TestConnectAuditTrailFailureDeniesAndDoesNotTunnel` 的第二阶段同理：`main_test.go:128` `logger.close()` 后请求，`handleConnect`（`main.go:209`）的 pre-flight 写（`main.go:225-233`）失败 → 打 403 → `main_test.go:132-135` 断言 403 且目标接受数不变。
- **结论**：这两条是负向用例的预期输出，在**任何一次**运行（含全绿运行）都会出现。

**(b) 一条 `sync … file already closed` 变体（路径 `…\TestTunnelWorksAcrossRealTLSThroughProxy666368954\001\proxy.jsonl`）—— 属于 `TestTunnelWorksAcrossRealTLSThroughProxy` 自己的 logger，是 cleanup 与 handler 的关闭/写入竞态，不是共享目录。**

- 路径逐字证伪"共享临时目录"：Windows 下 `t.TempDir()` 布局为 `<Temp>\<测试名><随机数>\<序号>`。该路径含测试名 `TestTunnelWorksAcrossRealTLSThroughProxy` 与序号 `\001\`，证明该 logger 文件在该测试**自己的**临时目录内。Go `testing` 保证每个测试的 `TempDir()` 唯一；且 `main_test.go` 全文件**无任何包级变量**（全文通读确认），每个测试自行构造 logger / allowlist / server / echo 监听器，不存在可共享的 rig。
- 该 `sync` 变体是**真实缺陷的噪声证据**（次要缺陷，非任何 DR 的成因）：`eventLogger.log()` 持 `l.mu` 做 Write+Sync（`main.go:110-134`），而 `eventLogger.close()` **不持锁**直接 `_ = l.w.Close()`（`main.go:150-155`）。`newTestProxy` 的 `t.Cleanup` 先 `server.Close()` 再 `logger.close()`（`main_test.go:225-226`），`server.Close()` 不等待被劫持隧道上的 handler goroutine 收尾；若 handler 正在写"closed"记录（`main.go:283-288`）时 cleanup 关闭文件，`Sync` 即报 `file already closed`。该测试自身断言在此之前已完成，**并不失败**——纯 stderr 噪声。

**(c) 归属判定依据 DR-5 失败行号本身完成自证**：DR-5 登记失败行为 `main_test.go:324: target accept count = 0, want 1`（REMAINING_SLICES.md DR-5 行）。该行位于 `if accepted.Load() != 1` 之后，其**前一行** `main_test.go:320-322` 的 200 状态行检查已通过（否则失败行应是 322 的 `want 200 handshake`）。同理 DR-2 失败行 `main_test.go:125` 之前 `main_test.go:121-123` 的 200 检查已通过。**结论：失败瞬间握手已成功、隧道已建立，写日志的 pre-flight 早已通过** ⇒ 任何"日志不可写导致 403/502"的路径与这四个失败行**在源码顺序上互斥**（日志破损会让代理在 `dialTunnel` 之前返回 403——`main.go:221-233`，永远到不了 200 检查通过的状态）。

### 1.2 任务 B —— 修法粒度判定：**共享根因（单一修复方案）**

**判定：DR-2 / DR-3 / DR-4 / DR-5 共享同一根因——`startTCPEcho` 的接受计数器断言与"客户端观察到 200"之间缺少同步点。** 机制级判据（不是"断言串相同"）：

- **同一状态**：四处失败读的是**同一 helper** `startTCPEcho`（`main_test.go:267-289`）创建的同型计数器（DR-2 变量名 `connections`、其余 `accepted`，均在 `main_test.go:274` 创建）。
- **同一写序**：计数器唯一自增点是 Accept 循环 goroutine 内 `accepted.Add(1)`（`main_test.go:280`），且它在 `listener.Accept()` 返回**之后**（`main_test.go:277`）才执行。
- **同一读序**：四处断言都是"`connectThroughProxy` 读到含 `200` 的状态行后**立即**读计数器"——`main_test.go:124-125`（DR-2）、`:323-324`（DR-5）、`:449-450`（DR-4）、`:468-469`（DR-3）。
- **破坏者与时机**：200 的发出点 `main.go:258` 紧随 `dialTunnel` 返回（`main.go:241`），而 `dialTunnel` 的 `net.Dial`（`main.go:287`）在 **TCP 内核握手完成（listen backlog）时即返回**——不要求对端应用层 `Accept()` 已返回，更不要求 echo goroutine 已执行到 `Add(1)`。客户端读到 200 → 测试读计数器之间，与 `Add(1)` 之间**不存在任何 happens-before 边**；echo goroutine 的调度延迟无上界。CI 满负载（尤其 Windows 腿，四次首跑红均发生在 Windows 腿）时该间隙超过"立即读"的时点 ⇒ `Load()==0` ⇒ 红；复跑负载不同 ⇒ 绿。DR 台账中"该片无任何 `.go` 改动"（DR-3 第 2 次 / DR-4 / DR-5 行）与复跑绿即与该机制完全一致（与改动无因果关联）。
- **DR-4 的加宽窗口**：多一跳 upstream 代理（客户端→代理→`TestConnectUsesUpstreamProxy` 的 httptest upstream→echo），链上多两个 handler goroutine，调度间隙更大，与"四处同族"不矛盾、反而相互印证。
- **DR-2 症状串的误归属澄清**：DR-2 行"症状"列把 `AUDIT TRAIL BROKEN (write … file already closed)` 与 `main_test.go:125` 并列。按 §1.1(c)，两者在源码顺序上互斥——125 行失败 ⇒ 200 已见 ⇒ 日志在 pre-flight 时完好；该告警串来自**同一 `Test` 步骤日志中反向用例的预期输出**（步骤日志交织所致）。DR-2 的真实失败仍是计数器竞态。
- **反例自查（证伪尝试）**：若四处根因不共享，应存在"非计数器竞态"的机制解释；逐一排除——(i) 日志句柄被共享/提前关闭：与 §1.1(c) 的源码顺序矛盾；(ii) 端口占用/监听失败：`net.Listen("127.0.0.1:0")` 与 `httptest.NewServer` 均取内核分配端口，且失败会是同步 `t.Fatal` 而非计数 0；(iii) 死锁：200 已回，与死锁矛盾。**无残留反例。**

**结论（可证伪判据）**：共享根因成立 ⇒ 按切片九字段，采用**单一修复方案**（下述 §2 的 Fix-1，一处 helper + 四个调用点）。若 Fix-1 落定后仍有 DR 复现，则本判定被证伪，需回到"4 个独立修复"路径——该判定自身的证伪门槛已写入 §4 风险 R3。

### 1.3 定论完备性

本判定在只读条件下**可定论**，无需追加探针实验：机制证据为纯源码顺序 + TCP 语义（`main.go:287` 内核握手、`main_test.go:280` goroutine 内自增、四处读点紧随 200），且失败行号身份（计数行而非状态行）构成自证。**唯一非源码依赖的事实**是"CI 复跑绿"，已由台账 5 行累计表给出（REMAINING_SLICES.md:483-491）。

### Fix-2（必需，同族潜在 flake 的预防）——完成记录的同步读取

| 文件 | 既有语义 | 拟改动 | 为什么必须改 |
|---|---|---|---|
| `main_test.go` `TestPlainHTTPForwardedAndLogged`（`client.Get` 返回后立即 `readLog` 并断言 `len(records) >= 2` 与完成记录字段） | handler 的完成记录写在 `io.Copy(w, response.Body)` **之后**（`handlePlainHTTP` 末尾），客户端读完 body 即返回 ⇒ 该记录可能尚未落盘 | 完成记录断言改用 `waitForRecord`（predicate：`event=="http" && decision=="allow" && bytesToClient != nil`）；首条 authorized 记录断言保留立即读（该记录在 RoundTrip 之前同步写，确定性） | 同一族的"handler goroutine 写 vs 测试立即读"竞态（未登记 DR 的 DR-6 候选）；不修则"首跑即绿"仍可能被它击穿 |

### Fix-3（推荐但可分离）——`eventLogger.close()` 加锁

| 文件 | 既有语义 | 拟改动 | 为什么必须改 |
|---|---|---|---|

**决定权**：Fix-1 + Fix-2 为本方案必需项（共同构成"单一修复方案"的完整面：Fix-1 消四处登记 DR，Fix-2 消同族未登记缺陷）。Fix-3 属 hygiene，② 实现时可纳入（便宜、低风险、在边界内），但**不作为验收必需**——其变异判据弱（见 §3 T7），单独标出以免稀释验收证据。

## 3. 测试点清单（可执行，含变异判据）

**变异判据总纲（本片特有口径，须写进 ② 实现与 ③ 测试文档）**：时序 flake 修复的"去掉修复即红"存在**不可确定性**——还原为立即读后本地大概率仍绿（这正是 flake 定义）。因此本片变异判据定义为两层：**（甲）注入底层真实缺陷**（使隧道/拒绝逻辑真的失效）⇒ 修复后的断言**确定性变红**（3s 截止内）；**（乙）结构消除性证据** = 本地 `go test -count=10` + 首跑 CI 3 连推双绿（切片验收①）。不允许用"还原修复后复跑绿"充当（乙）之外的反证。

**口径修正（③ 实测，2026-09-22；原判据的"确定性变红"成立，但归因断言需区分两类注入）**：

- **甲-i（按 §3 表所列注入点）**：allow 改错 / 去掉 `observe: true` / upstream 指向已关闭端口 / 删除完成记录写入 —— 实测四处**在更早的"状态行"断言上先红**（`want 200 handshake, got 403` / `want a 200 before the log is broken` / `observe mode must permit…` / `want 200, got 502`），因为状态行检查位于 `waitForAccepts` **之前**。⇒ "确定性变红"成立，但**不构成对 `waitForAccepts` 本身的证伪**。

## 4. 风险与缓解

| # | 风险 | 缓解 |
