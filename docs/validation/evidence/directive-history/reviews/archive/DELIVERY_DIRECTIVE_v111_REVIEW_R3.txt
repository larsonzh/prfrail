## 二、本轮新发现（§0–§1.7 首次全文覆盖）

### A1｜§0.1「类别判定标准」把门禁判据判给 CONTRACTS，与本准则 G1–G7 的权威地位冲突（High）

**位置**：§0.1:26（"涉及 wire 格式、状态转移、**门禁判据**、证据字段的 = **协议语义**（以 CONTRACTS 为准）"）；§0.1:24（"协议语义冲突以 CONTRACTS 为准"）；§0.1:18（协议与语义 = `CONTRACTS.md` / `schemas/` / 契约夹具）。

**冲突对象**：§6.3 的 G1–G7 全部是**门禁判据**，写在本准则内；C.0f（`GATES-EXT`）整片做的就是"**改门禁判据**"，走的是**本准则的切片流程**、改的是**本准则**、验收由本准则的 ⑥⑦ 完成。

**为何是 High**：这是**同词异指**——CONTRACTS 里的"门禁"是产品运行时的 gate（步内 gate / postflight / freeze），本准则 §6.3 的"门禁"是**仓库交付自检判据**，两者毫不相干，却共用"门禁判据"四个字。按 §0.1:26 的字面 + §0.1:24 的兜底（"协议语义以 CONTRACTS 为准"），**修改 G6/G7 判据时应以 CONTRACTS 为准**——这与 GATES-EXT 的实际做法和本准则 §0.1:21「交付执行纪律 = 本准则」直接相反。执行者只能临场解释，属静默失败类。

**建议修法**（二选一，写入 §0.1）：
1. 加术语消歧行：**"本节『门禁判据』指 CONTRACTS 定义的运行时 gate；§6.3 的 G1–G7 交付自检判据属**执行纪律**，以本准则为准。"**
2. 或把 §0.1:26 的"门禁判据"改为"**CONTRACTS 定义的运行时门禁判据**"。

### A2｜官方起跑模板 B.7.1 不满足 §1.6 触发词语法 ⇒ 照模板起跑会被判为日常档（High）

**位置**：§1.6:106–113（形态必须是 `切片：<id> <描述>` / `SLICE:<id> <描述>`…，且必须落在**消息首行前 20 个字符以内**）；B.7.1:883（官方模板首行 = `按 docs/DELIVERY_DIRECTIVE.md v[版本] 执行切片 [切片 ID / 名称]。`）。

**实测比对**：模板首行①**不含**任何规定的触发词形态（是"执行切片"而非 `切片：`）；②仅"按 docs/DELIVERY_DIRECTIVE.md v"就已超过 20 字符，即便把"执行切片"视作触发词也**必然落在窗口外**。⇒ 按 §1.6:112 的处置规则，主控应判 **不生效**、按 `[ROUTINE]` 处理，并标注"检测到疑似触发词但位置不合法"。

**后果链**：`[ROUTINE]` ⇒ ⑤⑥⑦ **全豁免**、**0 次付费调用**、不走 §5.1 流水线（§1.6:100）⇒ 用户**用官方模板起了一个切片级工作，却以日常档执行**，审查层与门禁（§5.0 前置硬门、角色就绪预检）被整体跳过。这与 H1/H3 同属"照章执行却静默走错"，且发生在**流程入口**——错一次，整片都错。

**附带缺陷**：§1.6 的"前 20 个字符"**未定义计数单位**（字节 / Unicode 字符 / 是否含前导空白、`>` 引用符、BOM），CJK 全角冒号与半角混用时尤甚 ⇒ 该判据不可机械核验，也无法写进 `gate.js`。

**建议修法**：
1. B.7.1 首行改为合规形态，例如：
   ```
   切片：[切片 ID] [描述]
   按 docs/DELIVERY_DIRECTIVE.md v[版本] 执行。
   ```
2. 或在 §1.6 增显式豁免："**附录 B.7.1 模板首行视为合法触发词**"，并定义计数单位（建议：按 Unicode 码点，跳过前导空白与 `>` 引用符）。
3. 两者都做时须**只保留一处权威**（§1.6 是唯一定义处，B.7 只放模板——符合 B.7 首段硬约束）。

### A3｜审查强度倒挂：纯文档切片必过 ⑦ 付费终审，普通生产代码的日常改动 0 审查（Medium+）

**位置**：§5.2:347 + :352（"简单/文档型"切片 **⑦ 独立终审不可省**）；§1.6:100（`[ROUTINE]` ⑤⑥⑦ 全豁免、0 付费调用）+ §1.6:104（日常档**可产生仓库改动**）；§1.6:118（边界②只挡"涉及状态机、崩溃路径、所有权、并发的**代码**"）；§1.7.1:146（"不影响契约语义的重构"属执行自由度）；R5.3（⑦ 不可省）。

**为何是缺陷**：边界②只枚举了代码的**四类高风险语义**。⇒ 一条**普通业务逻辑的生产代码改动**（新增函数、改返回值、改错误处理、加分支）既不触及四类语义、也不触及 CONTRACTS/schemas/fixtures/`.agent.md`/workflows/依赖 ⇒ **日常档即可改、即可提交，0 次独立审查**；而同一时刻改一个 `.md` 走 `[SLICE]` 却**必须**付费用 ⑦ 终审。风险与审查强度完全倒挂，且 §1.7.1 把"不影响契约语义的重构"列为可自主，进一步放大了这条通道。

**建议修法**（择一并写入 §1.6）：
- 在不可绕过边界增列一项：**"生产代码（`.go`）的任何新增或修改"**（保守）；或
- 明写裁决："**日常档允许改生产代码，前提是改动不触及边界①–⑥**"，并把该裁决登记进 §12.4 观察项 + 交 ⑦ 复核。
- 无论取哪案，都应把 §5.2「⑦ 不可省」与 §1.6「⑤⑥⑦ 全豁免」的**适用关系**写成一句显式口径（当前靠"ROUTINE 不走 §5.1 流水线"隐含推出，R5.3 字面仍可被读成覆盖所有改动）。

### A4｜§0.2 的 MAJOR/MINOR 规则自发布起从未被遵守（Medium）

**位置**：§0.2:30（`MAJOR` = **角色集或流水线结构**的变更；`MINOR` = 规则增补）；§0.3 各行。

**实测比对**：
| 版本 | 实际变更 | 按 §0.2 应定 |
|---|---|---|
| v1.7（:45） | 8 个角色文件删 `model` 字段 + 23 处标识消歧 ⇒ **角色集变更** | MAJOR |
| v1.9（:47） | 新增 §1.6 三档启动与触发词语法 ⇒ **流程结构变更** | MAJOR |
| v1.11（:49） | §5.1 新增 **⑧c** 环节 + §5.2/§5.3/§7.1/§11.3 配套 ⇒ **流水线结构变更** | MAJOR |

三次均只升 MINOR。⇒ 版本号不再携带 §0.2 所声明的信息，读者无法从 v1.0→v1.11 判断是否有结构变更；且 §0.2 是**硬要求**（"版本号 `vMAJOR.MINOR`；MAJOR = …"）。

**建议修法**：在 §0.3 表头或 §0.2 下加**裁决注记**：承认 v1.7/v1.9/v1.11 按现行定义应属 MAJOR 而当时按 MINOR 发布，并规定"自 v2.0 起严格执行"；或收窄 MAJOR 定义为"角色**增删**或流水线**步骤序列**变更"，使其与既有实践对齐。**不要**静默沿用——§0.2 与 §0.3 的裂口本身就是台账元数据不一致。

### A5｜§0.2 要求的"受影响的在飞切片"在 §0.3 无落点（Medium）

**位置**：§0.2:31（"每次变更必须：① 更新版本号与日期；② 在 §0.3 追加变更日志；③ **说明受影响的在飞切片**"）；§0.3:38–49（11 行变更日志，**无任何一行含该字段**，表头也只有 版本 / 日期 / 变更 三列）。

**为何是缺陷**：三项硬要求中第三项自 v1.0 起一次未执行，且**表格结构里没有它的位置** ⇒ 执行者无法照做（不是"忘了做"，是"无处可做"）。这与 §6.3 的原则（把人肉记忆换成机械断言）相悖，也无法被 G1–G7 检出（无判据）。

**建议修法**：§0.3 表增一列 `受影响的在飞切片`（历史 11 行按 §11.2 口径标注"**历史缺失**"），并在 §0.2 写明该列的填写口径（切片 ID + 影响性质：阻塞 / 需回写 / 无需动作）。

### A6｜§12.1「首个切片即为试点」与 §1.6「可建议、不擅自升级」无衔接（Medium）

**位置**：§12.1:647（"新准则或重大修订后，**首个切片即为试点**"）；§1.6:125（"**可建议、不擅自升级**：发现比预期大 ⇒ 回一句建议升级并**停下**等用户明说"）。

**为何是缺陷**：若用户以 `[SLICE]` 起跑（而非 `[PILOT]`），主控按 §1.6 只能建议、**不得擅自升为 `[PILOT]`** ⇒ §12.1 的"首个切片即为试点"即被跳过，而全文**没有**规定此时的处置（是停下等用户改发？还是按 [SLICE] 跑完并在报告中标注试点指标缺失？）。§12.1 的"预先声明量化指标"也随之落空。

**建议修法**：§12.1 补一句："**试点期首个切片若以 `[SLICE]` 启动，主控须在开场回执中提示『本片按 §12.1 应为试点』并按 §1.6 停下等用户确认；用户坚持 `[SLICE]` 时，须在验证报告中书面记录『未做试点指标声明』及理由。**"

### A7｜§2.2 注释称 R2.1 对产品层属"形式合规"，自我削弱硬规则（Medium）

**位置**：§2.2:185（"此时 R2.1『必须显式传 model』在这一点上属**形式合规**（传与不传是同一个模型，区别只在"声明上是否明确"）"）；R2.1:191（硬规则："不传 model"被禁止）。

**为何是缺陷**：R2.1 是**硬规则**，而 §2.2 的注释实质宣告它在三个产品层角色上"不传也可以"——这与 §5.0 步 2（"调用时**必须**显式传 `model`（R2.1）"）和 §2.5 的触黑教训（不传 model ⇒ 按 `agentName` 走默认值 ⇒ 可触黑）方向相反。虽然当前这三个载体确实同为 `deepseek-flash`、实际风险低，但**规则文本不应自我豁免**：一旦日后按角色配模型（§8.3 长期解），这条注释就会成为"可以不传"的先例。

**建议修法**：改写为**已知限制体例**（同 §8.3）：
> **已知限制（过渡态）**：三个产品层角色与主控同为 `deepseek-flash` ⇒ 显式传 model 在**当前**不改变实际模型。**本条不豁免 R2.1**——仍必须显式传；随 §8.3 长期解（按角色配模型）生效后本限制自动解除。

### A8｜§8.2 档位表缺 `[ROUTINE]` 行（Medium）

**位置**：§8.2:543–549（只有 简单 / 中等 / 复杂 / 高风险 / ⑦ Codex 五行）；§1.6:137（消歧段只说工作分级与思考档位是"两个不同维度"，未给 ROUTINE 的档位）；§1.6:100、:104（ROUTINE 不走 §5.1、**可产生仓库改动**）。

**为何是缺陷**：ROUTINE 不做切片类型判定（那是 §5.2 的事，而 §5.2 只在 §5.1 流水线内使用）⇒ **没有任何一行规定 ROUTINE 用什么档位**。而 ROUTINE 又能改仓库 ⇒ 一个产生改动的档位没有档位规定。§1.6:137 只做了"不混用"的消歧，没补这个洞。

**建议修法**：§8.2 增一行 `日常 [ROUTINE] | 沿用当前会话档位（不按本表设定）| — | — | —`，或在 §1.6 留痕段明写同一口径（**只写一处**，另一处引用）。

### A9｜§1.7.3 的区分原则覆盖不全（Medium）

**位置**：§1.7.3:157（判定方法："这个决定如果错了，需要修改的是**代码**还是**契约/方向**？——前者属执行自由度，后者属升级边界"）；§1.7.2:152–153（升级边界第 2 项"**超出切片范围的顺手修**"、第 3 项"**预算额度耗尽**"）。

**为何是缺陷**：判定方法只有两支（代码 / 契约或方向）。"顺手修"错了要改的是**范围**，"预算耗尽"错了要改的是**额度**——两者都落在两支之外 ⇒ 用 §1.7.3 的方法判这两项会得出"属执行自由度"的错误结论，恰恰是 §1.7.2 明令禁止的情形。

**建议修法**：§1.7.3 改为三支判定：**错了要改代码 ⇒ 自由度；错了要改契约/方向/范围/预算/授权 ⇒ 升级边界**；并补一句"清单未覆盖者按 §1.7.2 末项（有歧义即停下）处理"。

### A10｜停止态标记与 G1「三处状态一致」无豁免条款（Medium）

**位置**：§1.6:127–128（停止态报告头标 `**状态：已停止——未完成**`；台账保持 `🔄` 或改回 `⬜`，**由用户裁决**）；G1:399（"小节标题的状态符号 ↔ 状态表行 ↔ 完成记录行，**三处必须一致**"）；G7-d:448（已覆盖"停止态须带未完成标记"，但作用域是 `docs/validation/*.md` 的变更行）。

**为何是缺陷**：停止态**按设计**就是"报告标已停止、台账标未完成"的不一致形态。G1 无豁免 ⇒ 停止态切片收尾时 G1 必然被读成 FAIL（当前 G1 **未脚本化**、靠人工执行，风险潜伏）。G7-d 只解决了"停止态标记本身"，没解决"G1 的一致性判定"。

**建议修法**：G1 增豁免："**停止态切片（§1.6）不参与 G1 的三处一致性判定**，按 §1.6 的标记规则执行；G7-d 负责其完整性。" 并把这条与 OB-10 一并纳入下次 §6.3 修订。

### A11｜§1.2 九字段未挂接 §1.6 / §1.7 / §7.6（Medium）

**位置**：§1.2:66–74（九字段：标识/目标/依赖/规模/步骤/现状缺口/交付物/验收证据/边界）；§1.6（工作分级）；§1.7.3:159（执行自由度清单须进 ⑦ 审查输入包、⑧b 回写验证报告）；§7.6（探针额度须预先声明）。

**为何是缺陷**：切片定义是唯一入口，却**没有**"工作分级"字段、**没有**"执行自由度清单"字段、**没有**"探针额度"字段 ⇒ 三项要求在切片定义里无归口，验收时无据可查（叠加第 2 轮 M13：清单由谁在哪个环节产出、落在哪份文件，三者不一致）。

**建议修法**：§1.2 增三行字段（分级 / 探针额度 / 执行自由度清单落盘路径），并在 §1.7.3 明写"该清单由**主控**在 ⑥ 之后、⑦ 之前作为**编排工件**落盘至固定路径"。

### A12｜§1.6 触发词歧义：多触发词与计数单位未定义（Low）

- 形态要求 `<id> <描述>`，但**未定义 `<id>` 的字符集**（是否允许 `SW-1`、`B4 · AT-23` 这类含空格/点号的 ID——而 C.0g 用的正是 `DIRECTIVE-V1.11`，B4 用 `B4 · AT-23`）⇒ 含空格的 ID 会与"描述"边界混淆。
- "首行前 20 个字符"的计数单位未定义（字节 / 码点 / 是否计前导空白与引用符）。
- "命中多个触发词 ⇒ 不生效"与"日常档不设触发词"组合下，`切片：A 试点：B` 这类输入会被判 ROUTINE，而用户意图明显是切片级 ⇒ 建议改为"停下要求重发"而非"按 ROUTINE 判定"。

### A13｜§0.1 权威关系表缺本准则自身扩张出的三个域（Low）

§11.2 依赖的**切片台账 / ADR / 验收台账**路径仍无权威行（第 2 轮 M10 同源）；此外 v1.10 后新增的 **`tools/gates/`（门禁实现与判据真值源）** 与 **`.github/agents/`（角色集）** 也不在 §0.1 表内——前者是 G1–G7 的实际执行体，后者是 R2.5/G5-a/G5-b 的对象。建议在 §0.1 补三行。

### A14｜§1.1 与 §1.6 的"不适用 vs ROUTINE"消歧依赖交叉引用，易误读（Low）

§1.1:58 与 §1.6:104 已做消歧（"不适用"项不产生仓库改动；ROUTINE 可产生），但 §1.1 的"不适用：纯咨询式问答；单条命令的临时排查"与 §1.6 的"ROUTINE：对话式协作、小改动、出方案"在语义上高度重叠（"小改动" vs "临时排查"）⇒ 建议在 §1.6 给一句可判的分界（例如"是否落盘"）。
