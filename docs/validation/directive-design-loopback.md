## 3. ① 评估 OB-71（会话结论无回流）

### 3.1 编号来源：两个评估对象在台账中不存在（元证据）

- 全仓逐字检索 `OB-71` 至 `OB-79`：**0 命中**（含被 `.gitignore` 覆盖的 `tmp/**`；**检索时点 = 本片落盘前**，落盘后相关字样进入语料，故本结论以 HEAD 语料为准）；§12.4 的最大号为 OB-70 ⇒ 本片切片定义引述的『OB-71』『OB-76』**无台账登记**。

### 3.3 未回流结论的影响

- **规则与实操长期背离而不自知**：`modelId` 口径的偏差只能靠专项实测发现，而实测由用户触发 ⇒ 若无该次裁定，偏差会随每条新任务包继续扩散。
- **回退路径的「为什么」不可查**：若版本化准则被再次提案，此前「某种做法撑不住」的结论无处可引 ⇒ 同一论证要重做一遍，成本是本片这类评估片的数倍。
- **跨切片遗漏不可见**：未完成项只存在于各自切片的报告里，没有一处汇总 ⇒ 会话中的判断与仓库状态之间的差异无人核对（§5 的机制正冲这一点）。

### 3.4 与既有机制的关系（哪个覆盖、哪个不覆盖）

| 既有机制 | 覆盖 | 不覆盖 |
|---|---|---|
| §12.4 观察项台账 | 入口开放，是「未决 / 观察」的正式容器 | 只收未决项；**已定的设计结论**无容器（§3.1 即此类） |
| §11.2 回写口径 | 切片收尾的四类回写（报告 / `DEV_PLAN` / 台账 / ADR） | 只覆盖**切片自身**的证据；切片之间在会话里形成的结论无归属 |
| ADR 登记 | **正是**设计决策的回流载体（ADR-004 / ADR-011 / ADR-012 即例） | **无触发判据**（何时必须写 ADR），实际触发依赖用户与主控的记忆 |
| §12.5 缺口表 | 登记未落地的机制与角色 | 记的是「缺什么机制 / 角色」，不是「缺一条结论的归属」 |
| §7.8 收敛判据与 §12.1 试点指标 | 审查链的停止判定与试点达标 | 不含「结论是否已回流」这一维度 |

⇒ **缺口定位**：仓库缺的不是**容器**，而是**触发器与默认归属**——「哪类结论够格回流 / 何时必须落 / 落到哪一类载体」。

### 3.5 结论

- 值得补机制，但**不建议新增载体**（ADR 加 §12.4 加报告已齐备，再加一层必然重复并引入漂移）。
- 建议的最小形态 = **一条触发判据**：凡在会话中形成、且会改变后续执行或产品方向的结论，必须在**同一轮**内落到 ADR / OB / 报告中的至少一处并留指针；与 ③ 的机制合并落地即可，不必单独立项。
- 该判据属规则语义 ⇒ 本片**不落**，交用户裁定（§7 的 D-1）。

## 4. ② 评估 OB-76（RFC ↔ 准则映射缺失）

### 4.1 现状（引用矩阵，本片实测可复算）

| 方向 | 实测 | 说明 |
|---|---|---|
| 准则 → RFC | **2 处**，且均为偶然 | §6.3 的 G6-3 已知残余误报说明引用 RFC 的 `file:line`；OB-17 同源 ⇒ 无设计层指针 |
| RFC → 准则 | **0 处** | RFC 头部只指向 `DOCUMENTATION_PLAN` 的权威分域表 |
| 产品层权威文档 → 准则 | **0 处** | `PRODUCT_REQUIREMENTS` / `ARCHITECTURE` / `CONTRACTS` / `SECURITY` / `TEST_STRATEGY` / `BUSINESS_WORKFLOWS` 逐文件实测均为 0 |
| 产品层权威文档 → RFC | **各 1 处** | 均为头部「来源」指针 ⇒ 产品层的指针是**单层**的（指向历史来源，不指向纪律层） |
| 准则 ← 其他 | `DEV_PLAN` 1、`DOCUMENTATION_PLAN` 1、`REMAINING_SLICES` 4，另有历史稿与各验证报告 | 纪律层只被**自己的**台账与报告引用 |

- 唯一同时持有两层定位的文档是 `docs/DOCUMENTATION_PLAN{,_EN}.md` §1：其正文首段把 RFC 定位为「项目建议书与历史设计来源，不再承担全域唯一权威」，权威分域表另有「交付执行纪律 = `DELIVERY_DIRECTIVE`」行（该行第三列注「不适用（工程纪律，非产品设计来源）」）⇒ **定位关系存在、ID 级追溯关系不存在**（用户说「无正式追溯关系」成立，但「完全无关」不成立）。
- **既有指针先例**：RFC 对规范层**已在用**指针（§10.3 的标题即「状态机与恢复设计来源（规范已迁移至契约 §2.1）」）⇒「加一行指针」在本仓是成熟做法，不属新机制。
- **本片未发现已发生的语义冲突**：抽查 RFC 对 SessionBridge 的定位（`silent` 传输与 `cmd_<pid>.json` 等外部 adapter wire，RFC 内出现 7 处）与 ADR-012（AgentRunner 为正式执行端口、SessionBridge 降为消息桥）**相容**；RFC 内 `AgentRunner` 为 0 命中（该 ADR 晚于 RFC）⇒ 属**时间差**，不是矛盾。

### 4.2 影响

- **单向漂移无观测面**：产品层改动不触达纪律层，纪律层的流程变更也不触达产品层 ⇒ 两端各自演化，冲突只能被「恰好同时读两份文档」的人发现。
- **读者路径断裂**：按 `DOCUMENTATION_PLAN` 的阅读顺序能抵达准则，但反过来从 RFC 出发**到不了**纪律层，也到不了 ADR 给出的新定位（`AgentRunner` 在 RFC 内无出现）。
- **代价目前尚未显形**：本片只测到「跨层可查性近零」，没有测到已发生的缺陷 ⇒ 这条影响应按**风险**计，不按已发生损失计。

### 4.3 落点候选

| 候选 | 形态 | 代价 | 覆盖 | 不覆盖 |
|---|---|---|---|---|
| (a) 准则附录 A | 在 A.1「本准则的来源」增一行「产品定义层」 | 最小（准则内一行加指针） | 纪律层 → 产品层的单向指针 | 反向仍为 0 |
| (b) `DOCUMENTATION_PLAN` §1 | 在权威分域表增一行「跨层指针」，并把 OB-19 的通道写成明文 | 小（该文档已是唯一定位处，且不动准则语义） | **双向**（两层都从它出发） | ID 级追溯 |
| (c) 独立映射文档 | 新建 `docs/DESIGN_TRACEABILITY{,_EN}.md`（第 13 对文档） | 中（新增文档加每次规则变更的维护义务，并需配判据） | ID 级双向追溯 | 无（除成本与维护） |

### 4.4 结论

- **值得正式化，取最小形态**：建议落 **(b)**。理由 = ① 它是唯一同时持有两层定位的文档（本片实测）；② 不触碰准则的规则语义（符合本片约束）；③「加指针」在本仓已有先例（RFC §10.3）；④ 本片未发现已发生的漂移缺陷 ⇒ 按 §1.7.2 取保守形态。
- **不建议 (c)**：ID 级映射的实际需求未被证据支持（唯一的现成两层通道 OB-19 是逐条 OB、非系统性映射），且新增文档会立刻产生「新文档无判据」的缺口（与 §12.5 已登记的「判据自举风险」同族）。
- (a) 可作为 (b) 的补充（若希望纪律层自证其产品锚点），但不单独立项。

## 5. ③ 评估「任务包结项报告」机制

### 5.1 形态与关键边界

- 形态（用户已定）：任务包结束时的收尾文档 = **回看**（做了什么 / 完成什么 / 未完成及原因）+ **前瞻**（业务与技术上的新增 / 取消 / 改变 / 注意事项）。
- **关键边界（本片的结构性发现）**：准则现行的全部产出角色都**没有「业务方向」授权**——§1.7.3 明写「怎么做可自主，**做什么永远属于用户**」，§3.2 又禁止主控原创产品工件 ⇒ 若「前瞻」含业务方向，其**产出主体只能是用户**。
- ⇒ 机制必须写成**两份产物**：主控产出的「回看 + 待决问题清单」与用户的「前瞻裁决」，而不是一份由主控独撰的文档。

### 5.2 触发锚点与既有载体的关系

| 既有载体 | 粒度 | 覆盖「阶段收尾」 |
|---|---|---|
| §11.3 切片验证报告（含末项「下一步建议」） | 单切片 | 否 |
| 附录 C.0* 台账块 | 准则治理片 | 否（只覆盖准则治理） |
| §12.4 观察项台账 | 单条观察项 | 否（只收未决项） |
| §12.5 缺口表 | 未来机制 / 角色 | 否（是前瞻性缺口登记，不是收尾） |
| `DEV_PLAN` 段落与 `REMAINING_SLICES` 完成记录 | 单任务 / 单切片 | 否 |

- ⇒ **所有既有载体都是「单切片 / 单任务」或「单类元数据」的，没有「跨切片的阶段收尾」承载物**。
- 锚点已经有名字却没有落点：OB-19 的「Sol 战略回看问题集」、上一片启动前清单（`docs/validation/directive-cleanup-eval.md` 的既有-4）的「主控交接审计 = T027 结束时」，以及清单里的「S1 结束时」。
- **反向印证**：本片 ① 的三个例子都不是单切片的证据缺口，而是**跨切片的汇总缺口** ⇒ 与「阶段收尾无承载物」同源。

### 5.3 与 §12.5 已登记缺口的关系

- §12.5 已有同类缺口行：「复盘分析师（多切片数据复盘）| **积累执行数据后**」⇒ 机制的一半已登记（谁来做），缺的是**形态**（承载物）、**触发锚点**、**前瞻的归属边界**。
- 因此本机制**不需要新角色**：主控加用户即可承载；§12.5 的「复盘分析师」保留为**未来**增强（切片数足够多、需要横向数据复盘时）。

### 5.4 结论

值得做，三条理由：① 锚点已被反复引用却无承载物；②「未完成及原因」分散在各切片报告中、无人汇总 ⇒ 跨切片遗漏不可见（本片 ① 即此类）；③ 成本可控（模板加两个锚点加一条触发判据）且不新增角色。**前提**：前瞻必须拆成「主控的问题清单 + 用户的裁决」，不得由主控代写业务方向。

|---|---|---|---|---|---|
| **轻量** | 只加「结项报告」模板与触发锚点（沿既有报告体例） | 最小：一份模板加两个锚点写进准则的一行引用 | 阶段收尾有承载物；未完成项可汇总 | ② 的跨层可查性（仍为 0 指针）；① 的结论检索 | 痛点 = 阶段收尾无人写 |
| **中等** | 加「设计状态快照」文档（增量、可数、可机械检查）与结项报告 | 中：一份新文档加每阶段增量加至少一条判据（否则重复「有缺口无判据」） | 上述加当前设计状态可查、可比对 | RFC 版本化；结论的自动识别 | 痛点 = 设计状态不可查（本片实测支持：跨层引用近零） |
| **重型** | RFC 版本化加决策回流流程（把「何时必须落 ADR / OB」写成规则） | 重：RFC 升版机制加全流程义务加判据加维护成本（RFC 已近 190 KB） | 上述加双向 ID 级追溯 | — | 需要 ID 级双向追溯且能承担维护；**本片证据尚不支持**（未发现已发生漂移缺陷） |

**判据（只列，不清向）**：① 若痛点是「收尾无人写」⇒ 轻量已足；② 若痛点是「设计状态不可查」⇒ 中量是下限（轻量与现状同为「0 跨层指针」，见 §4.1）；③ 若痛点是「漂移必须被机械抓住」⇒ 才值得重型，且**必须先有一条能判红的判据**，否则等于把「判据自举风险」复制到新层。
