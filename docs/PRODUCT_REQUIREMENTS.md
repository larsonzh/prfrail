# ProofRail 产品需求与调研分析

[English](PRODUCT_REQUIREMENTS_EN.md)

日期：2026-09-06。状态：S0 评审稿，非发布承诺。权威：[RFC](RFC-proofrail-unattended-ai-engineering-product.md) §1、§9、§14、§17；工程纪律：[CODING_CONVENTIONS.md](CODING_CONVENTIONS.md)。REQ 编号用于实施追踪，不替换 RFC 的 R 编号。

## 1. 调研范围与事实基线

| 来源 | 证据/结论 | 限制 |
|---|---|---|
| 用户本轮确认 | whois v3.4.0 正式发布封板；SessionBridge v0.1.1 已在 GitHub/Gitee/Marketplace 发布并安装 | 作为项目输入采信；本轮未重新联网审计发布物 |
| RFC §2、§9 | whois 实践提出失控重试、基线污染、人工审批缺位和证据断链问题 | 是既有经验，不是外部用户访谈或市场统计 |
| 当前仓库 | Go 1.22 模块；CLI 仅 version 和 init/run 占位；11 个 internal 目录仅占位 | 不具备任务执行、安全隔离、恢复或验证功能 |
| 相邻 SessionBridge RFC §4、§7 | 可复用 silent 文本请求/回执；不提供 ProofRail 任务与审批语义 | 安装扩展不等于模型可用，更不等于代理有文件编辑工具 |

本次采用桌面需求分析和契约核对，不开展付费模型实验、竞品试用或批量联网调研。RFC 关于市场稀缺性的陈述仅作为定位假设，不能作为已证明的竞争优势。

### 替代方案与验证假设

| 方案类别 | 适用价值 | ProofRail 需要补足的控制责任 |
|---|---|---|
| IDE 编码助手/自主代理 | 提出或执行修改 | 独立验收、预算、可信基线、恢复证据；不假设任一厂商均缺少这些能力 |
| CI/脚本编排 | 重复执行固定验证 | 本地长任务的恢复、人工接管和候选接受事务 |
| Git 工作树/提交 | 版本保存与协作 | 无 Git 写权限时的当前工作树基线及未提交文件保护 |
| SessionBridge | 宿主消息与上下文传输 | 任务所有权、写租约、结构化变更、门禁、评审和发布 |

H1：小任务加确定性验收能减少人工盯守。用同一固定任务集记录人工干预次数、耗时及原因，对比手动脚本基线；没有测量前不承诺节省比例。
H2：最小 context envelope 能降低费用。记录输入/输出 token、模型、价格来源和每个已接受任务的总成本；供应商不给用量时标为估算，不伪装实测。
H3：与模型解耦降低接入成本。以无 AI 文件队列和 SessionBridge silent 两种通道通过同一套契约用例检验。

## 2. 用户与范围

主要用户是个人维护者和小团队。项目所有者决定范围、预算和发布；操作员运行、暂停、接管和处置；独立评审者批准或拒绝候选；AI 仅是受限执行主体。同一人可兼任维护角色，但变更生产者不得自行签发接受依据。

S0 完成规范、Schema/黄金样例和技术探针，再由用户批准 S1。S1 是 Windows 11 amd64 正式 CLI/TUI、Linux amd64 核心 CI，含 generic/C/Go、两种变更模式、manual-handoff、代码文档协同和两代自托管。S2 正式 Linux、多语言组合、Web、supervised；S3 任意生成脚本、多编辑器、inception。P 表示重要性，S 表示阶段，两者不可混用。

本轮是为 ProofRail 本身开展前期工程，不是在产品中实现 RFC R2 暂缓的 inception 功能。不改 whois 封板内容，不修改已发布 SessionBridge，不执行 Git 写入，不引入聊天系统、GUI 注入、云服务或数据库。

## 3. 用户场景与验收

所有场景均为 S1 必需；顺序表示开发依赖，不是降级优先级。

| 场景 | Given / When / Then | 价值 |
|---|---|---|
| US1 安全开始 | 给定含未提交文件的目录，建立 baseline 并运行三任务链；原目录保持字节不变，每任务仅继承已接受快照 | 不污染日常工作 |
| US2 可控失败 | 给定 T2 阻断型门禁失败；停止后归档并暂停；T3 不启动，恢复不消费失败候选 | 避免连续污染 |
| US3 人工参与 | 给定 code step 声明 manual-handoff；停进程后交租约；complete 后重新检查和验证，人工声明不等于 PASS | 支持真实调试工作 |
| US4 整体评审 | 给定公共 CLI 代码修改命中文档规则；文档未改或示例失败时整任务阻断；独立批准后代码和文档同快照接受 | 防止说明漂移 |
| US5 离线复核 | 给定已归档 run；离线核验事件、对象和 receipt；篡改、缺失、重排均不能判 PASS | 可追查、可交接 |
| US6 自托管 | 给定外部审计建立的 seed；构建候选并隔离重放；外部 oracle 比较失败时 seed 与正式版本不变 | 避免循环信任 |

边界场景：零任务/空 steps、未知字段/版本、路径逃逸、大小写冲突、共享 target、循环生成、租约冲突、部分写入、进程存活不明、磁盘不足、费用未知、模型超时、审批过期和 secret-direct 不受支持。每项必须有明确拒绝或暂停证据，不得推测成功。

性能测量方案（不是已测指标）：固定 10,000 文件/100 MiB、100 个 noop task 的非秘密夹具，在记录 CPU/RAM/磁盘/OS 的机器上测捕获、重放、峰值内存和证据大小；首次成功测量形成基线，之后同机中位数劣化超过 20% 触发调查，不能以删证据换性能。不设置未经测量的全平台秒级承诺。

## 6. 实体与成功标准

实体：chain 包含有序 task，task 包含 step；component/language scope 定义 target 所有权；snapshot 定义父子内容；hook 产出 evidence；ticket/attempt 约束修复；review/promotion receipt 证明接受；handoff 记录写租约。精确定义沿用 RFC §10、§18。

S1 成功标准：US1-US10（含 §8 新增场景）和全部 S1 强制反例通过；源目录 Git 状态和文件内容无引擎写入；三任务链中拒评/故障不推进；两模式恢复与人工交接可重放；Windows 原生及 Linux 核心 CI 有证据；自托管外部验收完成。交叉编译成功、空测试套件通过、模型声称完成均不计为产品验收。

## 7. 已批准边界、待落实事项与后续调研

2026-09-06，产品所有者批准 S0 规格冻结及 ADR §4：S0 新增付费调用为 0，Windows 11 amd64 正式/Linux amd64 核心 CI，当前与前一 minor（前一 minor 90 天），离线 Ed25519 签名策略，逐依赖许可审计，以及未来 whois 脱敏只读影子验证原则。精确依赖、签名主体/公钥、EOL 通知、安全评审者和具体 whois 输入仍待后续任务落实；本次不授权 S1 编码、付费调用、数据访问或发布，也不宣称 S0 完成。

后续若改为按金额授权，须以可界定最坏费用预留，无法界定则禁止自动调用；订阅模式只有在用户另行批准调用/token 硬上限并确认货币账单不可保证时才允许，详见 RFC §19.5。独立安全评审结论仍是进入 S1 前的阻断门禁。

S0 评审用一次结构化访谈确认：最常见三个任务、可接受人工介入点、证据保留需求、机器资源上限。S1 影子阶段用 US1-US6 的真实记录验证 H1-H3；结果和反例写阶段报告。外部市场规模、付费意愿及竞品性能不阻塞安全闭环，但对外宣传前必须另行取证。

## 8. 产品完整性评审（2026-09-06）

结论：执行引擎不能单独构成可用产品。依据 RFC §19，增加以下验收细化；仍为 28 个 REQ，不以条目数量冒充商业验证。PC 是既有需求的产品切片，不是另一套协议权威。

| 切片 | 业务缺口与用户结果 | REQ | S1 最小能力 / 后续边界 | 验收 |
|---|---|---|---|---|
| PC-01 | 首次使用难判断权限、费用和准备程度 | REQ-009/010/016/027 | 无 AI 示例、无副作用预览、unknown 原因与下一步；S2 图形向导/界面本地化 | AT-16 |
| PC-02 | 内部快照不能直接交付成果 | REQ-002/004/025 | 已接受快照导出至新目录，离线核验；不回写源树或发布；S2 外部 PR 集成评估 | AT-17 |
| PC-03 | 运行期间授权撤销、审批积压缺乏产品流程 | REQ-005/021/023 | 哈希绑定运行授权、撤销/过期阻断、待审批队列；S2 脱敏通知/RBAC | AT-18 |
| PC-04 | “可回滚”容易被误解为能撤销所有副作用 | REQ-012/023/024 | 声明副作用类别、默认禁外部写、恢复计划/脱敏诊断；S2 补偿协议另审 | AT-19 |
| PC-05 | 超时/重复请求可能仍计费，难解释成本和收益 | REQ-006/026 | 持久预留/结算、未知费用占用、共享上限、无默认遥测的本地报告；S2 趋势报表 | AT-20 |
| PC-06 | 升级、备份、停用、卸载和保留冲突未形成闭环 | REQ-019/025/028 | SBOM/支持矩阵、完整备份闭包/恢复演练、默认保留证据的卸载；S2 显式迁移 | AT-21 |

新增用户场景：US7 初次运行前只预览，确认无命令/模型调用后再授权；US8 从已接受结果导出交付包，在空目录验证且原树不变；US9 撤销运行授权后不再发起副作用，保留在途停止证据；US10 升级失败或停用后可从核验备份读取历史证据。各场景分别对应 AT-16、AT-17、AT-18、AT-21；成本和副作用反例由 AT-19/20 覆盖。

范围决策：S1 最小细化纳入修订后的 exit gate，但实施前须按 RFC §17.8 重新确认预算；S2 增强不得拉进首版。S3 的云服务、商业计费、团队管理须先验证真实付费需求，本轮不设计商业后台。现阶段以本地 CLI 的可安装、可试用、可恢复、可交付、可停用为产品验收。

价格未知时不能假设免费。对无法按次定价的订阅模型，只能承诺用户授权的调用/token 上限并标明货币账单不可保证；这是 REQ-026 的计量模式细化，不豁免授权与预算。收益评估用每个已接受任务总成本、首次完成耗时、人工介入和恢复成功率；仅本地记录，固定样例/机器，当前无实测结论。
