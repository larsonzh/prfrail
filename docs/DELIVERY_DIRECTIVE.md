## 1. 适用范围与切片模型

### 1.1 适用范围

- 适用：ProofRail 仓库内**一切需要交付产物的工程活动**（代码、契约、schema、fixtures、脚本、文档、证据包）。
- 不适用：纯咨询式问答；单条命令的临时排查（此类无需切片、无需审查，但不得产生仓库改动）。

### 1.2 切片（Slice）

**切片 = 最小可审查交付单元**。每个切片必须有一份**切片定义**，含：

| 字段 | 要求 |
|---|---|
| 标识 | `A0`/`B3c`/`DR-2` 式的稳定编号 |
| 目标 | 一句话，可判真假 |
| 依赖 | 前置切片或外部授权 |
| 规模 | S / M / M-L / L |
| 步骤 | 可勾选清单 |
| 现状缺口 | 为什么现在不做会出问题 |
| 交付物 | 文件级清单 |
| 验收证据 | 可机械核验的断言 |
| 边界 | **明确不做**什么（防扩范围） |

### 1.3 一次一片

同一时刻**只允许一个切片处于“进行中”**。

**并行口径（硬规则 R1.1）**：并行**只允许出现在主控自身的工具调用层**（例如同一条消息内发多条只读命令）；**不得并行调用多个子代理**（`runSubagent` 是串行阻塞的，见 R5.1）。跨切片并行仅在用户显式授权时允许，且**只读**；**不得**并行跑会互相干扰的实机实验（进程 / Job Object / 端口 / 临时目录），见 §四.11 原件（附录 A）。

### 1.4 协议先行（硬规则）

凡语义变化，顺序固定：**CONTRACTS 双语 → schema / fixtures → 代码 → 聚焦测试 → 文档回写**。不得让代码先行。

### 1.5 工作区卫生

- 开工前工作区必须干净；未提交的历史改动必须先由用户处置（提交 / 暂存 / 丢弃）。
- 临时产物只放仓库根 `tmp/`（gitignored），**用完立即清除**，不得跨切片遗留。
- 不得在切片运行期间并行跑会互相干扰的实机实验（进程 / Job Object / 端口 / 临时目录）。

## 2. 角色与模型白名单

### 2.1 角色模型（三层）

| 层 | 角色 | 职责一句话 | 可否写文件 |
|---|---|---|---|
| **编排层** | 主控 | 指挥、调度、门禁、证据、兜底、报告 | 仅编排工件（§3.2） |
| **产品层** | 实现者 / 测试工程师 / 文档工程师 | 各自领域的**唯一**产品工件生产者 | 是 |
| **审查层** | 架构师 / 预审员 / 独立扫描员(③.5) / 独立终审员(④) | 只读推理与门禁 | **否** |

### 2.2 角色—载体—模型三元组（**必须显式传 `model`**）

| 角色 | 调用点 | `agentName`（载体） | 必须显式传的 `model` | 与主控同模型？ | 工具能力 |
|---|---|---|---|---|---|
| 架构师 | ① | `deep-reasoner` | `DeepSeek V4 Pro (deepseek)` | 否 | 只读 |
| 预审员 | ⑤ | `deep-reasoner` | `DeepSeek V4 Pro (deepseek)` | 否 | 只读 |
| 实现者 | ② | `prfrail-implementer` | `DeepSeek V4.1 Flash (deepseek)` | **是（过渡态）** | 读写 + 执行 |
| 测试工程师 | ③ | `prfrail-tester` | `DeepSeek V4.1 Flash (deepseek)` | **是（过渡态）** | 读写 + 执行 |
| 文档工程师 | ⑧ | `prfrail-documenter` | `DeepSeek V4.1 Flash (deepseek)` | **是（过渡态）** | 读写 + 执行 |
| 独立扫描员 | ⑥ | `independent-reviewer` | `MAI-Code-1.1-Flash (copilot)` | 否 | 只读 |
| 独立终审员 | ⑦ | `independent-reviewer` | `GPT-5.3-Codex (copilot)` | 否 | 只读 |

> **“与主控同模型”列的含义**：标“是（过渡态）”的三个产品层角色与主控同为 `deepseek-flash` ⇒ **不只档位不可分离，模型能力本身也不可分离**（见 §8.3）。这是一个**过渡态配置**：此时 R2.1 “必须显式传 model” 在这一点上属**形式合规**（传与不传是同一个模型，区别只在“声明上是否明确”），真正的解是按角色配不同模型。

**载体就绪状态（截至 2026-09-21，实检）**：`deep-reasoner`（架构/预审）与 `independent-reviewer`（⑥/⑦）**已就绪**；`prfrail-implementer` / `prfrail-tester` / `prfrail-documenter` 已由切片 **SW-2 创建完成，且三个载体均通过实机探针**（各自完成“创建→读回→删除”，残留 0；证据见 `docs/validation/sw-directive-switchover.md` §5）⇒ **§2.2 列出的七个载体全部就绪**。**唯一遗留**是 **SW-3**（11 个既有生成型角色文件的编码归一，待授权）——它**不影响** §5.0 的角色就绪预检，因为预检只针对本表列出的七个载体。

**硬规则 R2.6（调用隔离，防锚定）**：① 架构师与 ⑤ 预审员是**同一载体的两次独立调用**，**上下文不共享**——⑤ 只能收到「方案书 + 原始实现 diff（**路径**）+ 契约原句」，**不得**收到 ① 的对话历史、主控的实现期推理或任何实现前的假设。⇒ **防锚定靠“调用隔离”，不靠“角色或模型分离”**；不得以“同载体”为由取消 ⑤，也不得把 ① 的推理传给 ⑤。

**硬规则 R2.1**：`runSubagent` **不传 `model` 时会静默回落到会话主模型**。因此"不传 model"被禁止；每次调用都必须在任务包中写明模型串。
**硬规则 R2.2**：只写现役模型 ID。Flash 只写 `deepseek-flash`（`deepseek-v4-flash` 与 `deepseek-v4-flash-vision-exp` 已列 `LEGACY_FLASH_MODEL_IDS`，禁止使用）。
**硬规则 R2.3**：**子代理深度 ≤ 1，禁止调用链**（不得出现 主控 → 子代理 → 另一模型）。因此带 `agent` 工具的编排型代理**不得进入角色集**（见 §2.4）。
**硬规则 R2.4**：角色文件是**角色集的可复现来源**。新增/修改角色必须走版本控制（见 §2.6）。

### 2.3 模型自报不可信

子代理**无法可靠自报**模型与档位（实测：Flash 子代理自报 `GitHub Copilot（系统提示声明为 DeepSeek V4.1 Flash）| vendor=unknown`）。⇒ **禁止**以"子代理说自己是某模型"作为验收证据；模型与档位只能由 operator 在 UI 侧设定并在任务包中**记录**。

### 2.4 禁止清单（黑名单）

以下模型**不得调用**，任何情况下：Luna、Gemini 系列、Terra、GPT-5.4、**Sol（战略主控）**、Kimi 系列、以及"任何其他模型做拟稿/复核/格式/清单/验证/统筹"。

**编排型代理禁用**：`sol-orchestrator`（`model: gpt-5.6-sol`，`tools` 含 `agent` 且声明 `agents: [...]`）——
- 它带调用链能力，违反 R2.3；
- 其模型在黑名单内，且不显式传 model 会回落成主控自身 ⇒ 产生"假编排"；
- 其自带的 `routing` / `Kimi K3` / `ultra 档` 规则与本准则白名单、成本上限**不一致**；
- 依据其自身配置 `strategy.manual_override.detection: 非 Sol 主控会话即视为手动模式，跳过全部子代理自动编排`——**当前主控非 Sol 时，它的自动编排按设计即关闭**，本就无需启用。

**唯一例外**：③.5 层放行 `mai-code-1.1-flash`；Haiku 仅在 §7.2.3 的启用前置条件全部满足时作为 ③.5 补充限时放行。

### 2.5 角色集的版本化（D1-a 选型）

**规则 R2.5**：`.github/agents/*.agent.md` **一律**纳入版本控制（**含既有生成型角色文件**）；**生成器工具链不入库**。

- 版本控制范围：`.github/agents/*.agent.md`（角色定义，**含既有 11 个**原由 `sol-orchestrator` 生成的文件）。
- 继续忽略：`.github/agents/sol-orchestrator/`（生成器工具链与其 `__pycache__`、`_discovered_models*.json`、定价表）、`.github/agents/*.managed.json`。
- **头注硬规则**：**全部 14 个角色文件**（3 个 `prfrail-*` + 11 个既有）的**头注必须位于固定位置**：frontmatter 结束后**首个非空行**必须**逐字等于**下面这一行：
  `> **非生成物（sol-orchestrator 已按 DELIVERY_DIRECTIVE §2.4 禁用）：手工维护；不得由生成器覆盖。**`
  **机械判据**：① 解析 frontmatter 结束位置，取`此后首个非空行`与头注文本比较，**必须相等**（**不接受**“文内出现即可”——否则头注移到正文也能通过，⑦ 第 3 轮 Low 发现）；② 辅证：`grep -L "非生成物（sol-orchestrator 已按" .github/agents/*.agent.md` **无输出**。
- **若日后启用该生成器**：必须先把 `_config.yaml` 与生成脚本一并纳入版本控制，重跑生成并与手工文件**逐字比对**，差异须解释后方可切换。
- **已知隐患（已登记 OB-8，本片不修）**：实检 11 个既有角色文件中有 **8 个**（非 9 个；⑦ 第 3 轮纠正）的默认 `model` 属 §2.4 黑名单——族分解：**Terra 3**（`expert-arbiter`/`heavy-builder`/`planning-specialist`）、**Luna 2**（`fast-implementer`/`quick-researcher`）、**Gemini 1**（`context-researcher`）、**GPT-5.4 1**（`standard-builder`）、**GPT-5.6-Sol 1**（`sol-orchestrator`）；非黑名单 3 个：`deep-reasoner`（`deepseek-v4-pro`）、`independent-reviewer`（`gpt-5.3-codex`）、`quick-verifier`（`deepseek-flash`）。其中大部分**不在 §2.2 角色表内** ⇒ 其默认模型可能绕过 R2.1 而被误用。⇒ 当前防线 = “**调用必传 `model`**（R2.1）+ §2.2 角色表只列白名单载体”

### 2.6 角色文件的最小契约

每个角色文件必须含：`name` / `description` / `tools` / `user-invocable` / `target`，以及正文中的**职责、输入、输出契约、禁止项**四段（模板见附录 B）。**`model` 键必须省略**——**不得**写空值，也不得写具体模型。理由（均为 2026-09-21 实测）：① 写 `model: ""` 会使 VS Code **加载不到该载体**（`runSubagent` 报 `Requested agent '...' not found`；隔离验证：加空值键⇒失败，删键⇒恢复）；② 写具体模型值会与 R2.1“必须由调用方显式传入”冲突并诱发静默回落。⇒ **省略键**是唯一同时满足“可加载”与“不设默认模型”的形态；正文必须以一行显式声明“`model` 留空，由主控在 `runSubagent` 中显式传入（R2.1）”。

**过渡条款**：本准则启用后**新建**的 `prfrail-*` 角色文件必须**立即**满足四段契约；由 `sol-orchestrator` 生成器产出的既有角色文件（`deep-reasoner`、`independent-reviewer` 等）**豁免**正文段落要求——它们只作为 `model`/`tools` 载体使用，其职责/输入/输出/禁止项**以本准则 §4.2 与附录 B 为准**。

## 3. 主控职责与边界

### 3.1 主控做什么

1. **任务分解与派单**：把切片拆成原子工作包，为每个包写明：输入材料、期望输出、验收条件、**模型串**。
2. **上下文最小化投喂**：只给子代理完成任务所必需的材料；凡涉及审查方，一律给**证据路径**而非转述（§6.2）。
3. **门禁执行**：在关键节点亲自运行 build / vet / 聚焦测试 / 编码门禁 / 收尾自检（§6）。
4. **审查调度**：按 ⑤→⑥→⑦ 顺序调度，按结论决定通过或打回；执行闭环纪律（§5.3）。
5. **证据管理**：把 diff、门禁输出、探针结果落盘并交付路径（§6.2）。
6. **兜底**：见 §9。
7. **停点**：§10.4。

### 3.2 主控不做什么（硬边界）

- **不原创产品工件**：不写生产代码、测试代码、CONTRACTS/schema/fixtures、验证报告正文。定位到问题后**指派对应子代理**修复。
- **不代替审查方下结论**：不得自行判定"预审/扫描/终审通过"。
- **例外（编排工件，允许且必须由主控产出）**：任务包、状态表、证据文件（diff/日志落盘）、异常与兜底记录、报告**装配**（把子代理产出与门禁结果汇总成报告，不改写其结论）、台账与状态标记回写。
- **机械集成豁免**：把子代理产出的补丁落到文件属**机械集成**，不算"写代码"，但必须过三重校验：① 落盘前后 diff 行数一致；② 涉及 `.md` 时编码门禁通过；③ 落盘后立刻跑聚焦门禁。

### 3.3 主控的自检义务

主控必须对**自己的每一轮改动**跑 §6.3 的收尾自检；发现不一致**当场修**或指派子代理修，不得留给用户或审查方发现。

## 4. 子代理职责与输出契约

### 4.1 通用输出契约（所有角色）

1. **结论行**：最后一行必须是规定枚举（如 `PRE-REVIEW: PASS` / `FINDINGS` / `RE_` / `INDEPENDENT SCAN: ...`）。
2. **可定位**：每条发现必须带 `file:line`（或 `file:?` + 逐字引用）；不得只有散文。
3. **严重度**：`Critical / High / Medium / Low` 四级，定义见 §4.3。
4. **建议修法**：给出可直接落笔的文本或补丁；涉及双语时给中英双句。
5. **不得扩范围**：不得建议解除冻结结论、跳过审查、降低门禁。
6. **只读角色不得改文件**；发现需要改，交给主控派单。

### 4.2 逐角色职责

| 角色 | 输入 | 必须产出 | 禁止 |
|---|---|---|---|
| 架构师 | 切片定义、相关契约、历史裁决 | 《架构设计方案书》：结论、改动点清单（文件级）、测试点清单（可执行）、风险与缓解 | 写代码；**把实现前的推理上下文带入 ⑤**（防锚定靠调用隔离，见 R2.6——不得向 ⑤ 传递 ① 的对话历史或实现期假设） |
| 实现者 | 方案书、契约、待改文件精确上下文 | 代码 diff + 实现说明（覆盖了哪些改动点、有无未覆盖） | 做架构决策；写测试；改非代码文档 |
| 测试工程师 | 方案书测试点清单、实现 diff | 测试 diff + 覆盖矩阵（正例/反例/边界/并发/崩溃） | 改生产代码；改测试基础设施 |
| 文档工程师 | 方案书、实现 diff、测试 diff、现行文档 | 文档 diff + 变更摘要 | 改代码；加主观评价 |

| 独立扫描员（③.5） | diff、契约原句 | Section A–E 报告 + 结论行 | 改文件；参考他人清单（保持独立） |
| 独立终审员（④） | 最终 diff + 契约原句（**首轮不附任何清单**） | 安全 / 架构一致性 / 完整性 / 测试反例四段 + 结论行 | 改文件；首轮参考任何中间结论 |

| 级别 | 含义 | 处置 |
|---|---|---|
| Critical | 数据丢失、安全边界失效、静默错误结论 | 必须修复并重跑该审查环节 |
| High | 功能失效、崩溃、契约冲突 | 同上 |

## 5. 工作流（串行流水线）

### 5.0 启动（切片入口）

0. **前置硬门（准则切换期）**：切片 **SW-1**（引用改写）与 **SW-2**（角色载体就绪）必须均已验收通过；否则本准则的流水线**不得启动**（防双准则并行）。两者的定义与验收命令见附录 C.0 与 C.0b。
1. 用户提供**切片定义**（§1.2 的九字段）或指明其在台账中的位置。
2. 主控校验：依赖是否满足、工作区是否干净（§1.5）、是否还需要预算/授权（§7.6）；并做**角色就绪预检**——逐个核对 §2.2 所需角色文件存在、**该文件不含 `model` 键**（写空值会导致载体加载失败，见 §2.6 / §9.3）、**写文件类角色的 `tools` 含 `edit`**（只传 model 不选对载体拿不到写权限），且**调用时必须显式传 `model`**（R2.1）；任一不符 ⇒ 标记“角色阻塞”并停下。
3. 主控判定切片类型并**设定档位**（§8.2；一经设定，连续运行中不切换）。
4. 生成**任务包**（每包含：输入材料、期望输出、验收条件、`model` 串），随后进入 ①。
5. 任一项不满足 ⇒ **标记“依赖阻塞”并停下**，不得自行推断或降级执行。

### 5.1 流水线

```
①架构（如需） → ②实现 → ③测试 → ④主控集成+门禁 → ⑤预审(V4 Pro)
   → ⑥③.5 扫描(MAI) → ⑦④终审(Codex) → ⑧a文档初稿 → ⑨原生验证 → ⑧b文档定稿 → ⑩停点(等授权)
```

**说明：⑧ 分两步（防文档滞后）**——**⑧a 初稿**在 ⑦ 之后立即做（不阻塞 ⑨，先把已定结论落盘）；**⑧b 定稿**在 ⑨ 之后做，吸收原生验证结果与任何回退修复。⇒ 避免“⑨ 失败导致文档重写”。

**硬规则 R5.1（串行）**：`runSubagent` 是**串行阻塞**的（agents 不异步、不后台）。"并行"只允许出现在主控自身的工具调用层（例如同一条消息发多条只读命令），**不得**在任务包或流程图中承诺子代理并行。
**硬规则 R5.2（每环有产物）**：每一环必须留下可核验产物（diff / 报告 / 门禁输出 / 证据文件）。无产物的"已通过"不成立。
**硬规则 R5.3（按规模裁剪）**：角色启用按切片规模裁剪（§5.2），但 ⑦ 独立终审**不可省**。

### 5.3 闭环纪律（硬规则）

任一环节失败或需整改时，**修复后必须重新执行该环节本身**，禁止跳步：

| 环 | 失败后的动作 |
|---|---|
| ① | 修订方案/契约后**重跑 ①** |
| ②③ | 修代码/测试后**重跑④聚焦门禁** |
| ⑤ | 消除偏离/反例后**重跑 ⑤** 确认清零 |
| ⑥ | 修复后**重跑 ⑥**，直至无 Medium+ |
| ⑦ | 修复后**重跑 ⑦ 复审**，直至无 Medium+（**不得自行判定通过**） |
| ⑧a/⑧b | 文档不一致即回 ⑧a/⑧b 重写 |
| ⑨ | 就地修复重跑；**连续 2 次失败升级 ⑤ 复查**；仅当架构假设被原生证据证伪才回退 ① |

## 6. 门禁与证据

### 6.1 基础门禁（每次改动后）

| 门禁 | 命令 / 判据 |
|---|---|
| 格式 | `gofmt -l .` 输出为空 |
| 构建 | `go build ./...` exit 0 |
| 静态检查 | `go vet ./...` exit 0 |
| 单元测试 | `go test ./...` exit 0（记录 ok 包数与 FAIL 计数） |
| 契约夹具 | 涉及契约时补跑 Node 合同检查（夹具计数必须同步） |
| 编码 | `.md`/`.ps1` = UTF-8 **with BOM** + LF；`.json`/`.go` 等 = **without BOM** + LF |

### 6.2 证据落盘义务（硬规则 R6.1）

**所有审查类子代理都没有 `execute` 能力**（实测：`deep-reasoner`、`independent-reviewer` 仅 `read`+`search`）。因此：

- 审查前，主控必须把**原始 diff** 与**门禁原始输出**落盘（`tmp/` 或 `.tmp/` 下，用完清理），并把**路径**交给审查方。
- **禁止**只把 diff 摘要/转述贴进 prompt 就当"已提供证据"。
- 先例：B3c ④ 复审曾因"未提供原始 hunk"整轮作废；改为落盘 `tmp/b3c-review.diff` 后一次通过。

### 6.3 收尾自检门禁（五类机械检查，**强制**）

**位置**：`tools/gates/`（纳入版本控制）。**触发**：任何切片收尾前、任何 docs-only 提交前。
**原则**：把"人肉记忆"换成"机械断言"——本准则不假设任何角色不会忘事。

| # | 检查 | 判据 |
|---|---|---|
| G1 | **状态标记一致性** | 小节标题的状态符号 ↔ 状态表行 ↔ 完成记录行，三处必须一致（如 B3c 曾出现标题仍 `⬜` 而状态表已 ✅） |
| G2 | **占位符残留** | 全文不得残留"待…回填""尚未提交""待同轮授权""pending the push"等占位（切换后这类必须已被事实替换）。**扫描范围必须排除本行自身的规则引文**——否则本行引用的被禁字符串会被自己判为违规（**自指缺陷**，2026-09-21 实测：§6.3 自扫得 4 条假阳性）；实现上按"引号内被禁串 + 所在行含『不得残留』⇒ 跳过"处理 |
| G3 | **双语对称** | (a) **改动行数对称**：对每个被改动的 CN/EN 文档对，`git diff --numstat` 的 新增/删除 行数必须相等（2026-09-21 实测：本片 6 对全 PASS）。**不要求**全文行数或加粗标记数相等——既有双语对历史就不对称（`REMAINING_SLICES` 501/488、`B2-EXTERNAL-ENFORCEMENT` 270/315），“全文相等”对它们不可满足（**自指缺陷**，同 G4b）。(b) **关键字段对齐（作用域 = 变更行，非全文）**：`git diff -U0` 的**新增行**中，CN/EN 两侧的**提交号 / run 号 / 状态枚举 / 结论枚举**计数必须相等——行数对称**不能**证明语义未漂移（⑦ 首轮 Medium 发现）。**不得**用全文比对：全文差异可能来自历史遗留（实测：`B2-EXTERNAL-ENFORCEMENT` 全文 10/9，而变更行 0/0）。 |
| G4 | **编码 + 异常字** | (a) BOM+LF 逐文件核验；**作用域 = 本次待提交的变更集**（≠ 整棵脏树）。(b) **异常字扫描**：新增内容的 CJK 字符集合 ⊖ HEAD 全库 `.md` 语料 = **差集**；差集再 ⊖ `tools/gates/cjk-newwords.txt`（合法新词白名单，每字须附理由与上下文摘录）**必须为空**。⇒ 原表述“差集必须为空”对任何新文档都不可能满足（2026-09-21 实测：51 KB 新文档差集 7 字，逐字复核全为合法新词），故此改用**白名单**把“人工判断”固化为可机械重跑的断言。（本准则的由来：曾把「拒绝」误写为「拒绍」5 处） |
| G5 | **变更集契约** | 三者一致：**暂存清单** ↔ **报告声明的改动集** ↔ **台账证据引用**；`git add` 必须逐个文件（禁止 `-A`）。**结构化输入**（脚本读固定 JSON，避免只能靠人工读报告）：`{stagedFiles[], declaredFiles[], evidenceRefs[], addMode}`；`addMode` 非 `explicit`、或三集合不等 ⇒ **退出码 2** |

**子规则 G1-b（版本元数据一致性，2026-09-21 新增）**：**文件头声明的版本号必须等于 §0.3 变更日志最新一行的版本号**，且头部日期与最新行日期一致。机械判据：从文件头提取 `版本：vX.Y`，**仅从 §0.3 表格区间内**提取最后一行的 `vX.Y`（**不得全文扫描**——其他表（如附录 C.1 的 v3.1 对照表）也会出现 `| vN.N |` 形态，全文扫描会得 5 条假命中，实测），**两者必须相等**（不相等 ⇒ G1 失败 ⇒ 停止提交）。

## 8. 档位（思考模式）规则

### 8.1 基本事实（实测）

- 档位是 **API 层参数**；模型**无法感知、确认或自改**档位，子代理自报档位亦不可信（实测 `effort=unknown`）。
- 档位由 **operator 在开跑前设定**；**连续运行中无法动态改变**。
- `deepseek-flash`（主控与产品层同用）支持 `low / high / max`，默认 `high`。

### 8.2 档位设定（按切片类型，**启动前一次性设定**）

| 切片类型 | 主控 | 架构师/预审员 | 产品层（实现/测试/文档） | ③.5 / ⑦ |
|---|---|---|---|---|
| 简单 | High | — | 与主控同档（见 §8.3） | 各自的模型默认/固定档 |
| 中等 | High | Max | 同上 | 同上 |
| 复杂 | High | Max | 同上 | 同上 |
| 高风险 | **Max** | Max | 同上 | 同上 |
| ⑦ Codex | — | — | — | **Extra High（固定）** |

### 8.3 同模型角色的档位不可分离（**已知限制**，D2=A）

主控与产品层**同为 `deepseek-flash`** ⇒ 二者的档位是**同一个设置**，无法在连续运行中分别为"主控 High / 实现者 Low"。

- **接受同档**：默认整体取 **High**。
- **需要 Max 时**：① 在**任务启动前**把 Flash 档位配为 Max；或 ② 任务进行中**暂停 → 改档 → 继续**（暂停前后必须重跑一次门禁确认状态）。
- **长期解**：为产品层配置**不同的模型**（按角色配模型），届时本限制解除。

### 8.4 档位变更的记录义务

每次改档必须在报告"环境与档位"表中记录：设定时刻、档位值、是否经过暂停、暂停前后门禁结果。

## 9. 主控兜底与异常处理

### 9.1 兜底触发场景

| 场景 | 主控行动 |
|---|---|
| 子代理输出为空 / 明显不合理 | 重新裁剪上下文后**重试 1 次**；仍失败 ⇒ 记异常，换备用载体或降级工序 |
| 子代理连续 2 次失败 | 暂停该环，输出诊断报告，**标记需人工介入** |
| ⑤/⑥/⑦ 结论互相矛盾 | 主控**根因仲裁**：复现最小反例 → 判定谁错 → 决定修复路径 → 写入报告 |
| 门禁异常且非代码问题 | 检查环境/依赖/配置；必要时重建环境（不得改动生产代码掩盖） |
| 边界模糊 / 依赖未满足 | 向上回溯切片定义，**标记"依赖阻塞"并停下**，不得自行推断 |
| 原生验证失败且原因不明 | 逐层剥离定位根因 → 指派对应子代理修复 |

### 9.2 兜底原则

1. **兜底不等于代写**：定位问题后仍指派产品层角色修复；主控只做机械集成与门禁。
2. **每次兜底必须记入报告"异常处理"章节**（场景、定位过程、指派路径、结果）。
3. **阈值合并**：同一切片兜底介入 **> 3 次** ⇒ 自动标记"高风险切片"并**暂停等人工审核**；与 §5.3 的"⑨ 连续 2 次失败升级 ⑤"**共用同一计数**，不得形成两套并行阶梯。

### 9.3 已知异常模式（先验清单，供快速定位）

| 模式 | 症状 | 处置 |
|---|---|---|
| SCM 陈旧显示 | 编辑器显示"未跟踪"但 git 干净 | 以 `git status --porcelain -uall` 等四条命令为准；刷新/重启编辑器 |
| 终端假中断 | 命令回显 `^C` 但实际已执行 | 用 `git log`/文件状态复核，不重发破坏性命令 |
| 字符级误写 | 中文字符被写成形近字 | 跑 G4 异常字扫描 |
| 工具匹配宽松 | 替换工具对形近 oldString 仍报成功 | 改后必跑机械断言，不信任"success"回显 |
| 编码默认值 | 新建 `.md` 无 BOM / CRLF | 落盘后立即跑编码门禁并纠正 |
| **写文件工具产出 CRLF** | 新建文件经写文件工具落盘后行尾为 `0d 0a`，违反 LF 硬规则 | SW-2 探针实测（31 B 含 CRLF）。**新文件无既有行尾可推断 ⇒ 必定 CRLF**；已有文件通常保留原行尾。⇒ 任何“新建文件”落盘后必须用显式 `UTF8Encoding($false)`（无 BOM）或 `UTF8Encoding($true)`（`.md` 有 BOM）归一化行尾并回读核验。**补测（2026-09-21，探针 4/4）**：写文件工具对 `.md` **同样不保真**——产出**无 BOM + CRLF**（54 B，`first3=23 20 50`，`0D×2`）；按字节修正为 BOM+LF 后 55 B 全项通过。⇒ **`.md` 落盘后必须显式补 BOM 并删 CR**，不得依赖工具或编辑器自动处理 |

| **`model: ""` 使载体加载失败** | 角色文件写了空值 `model:` ⇒ `runSubagent` 报 `Requested agent '...' not found` | 2026-09-21 实测（隔离验证：加空值键 ⇒ 失败；删键 ⇒ 恢复）。⇒ 角色文件**省略** `model` 键（§2.6） |

**规则 R9.1（故障模式库持续增长）**：§9.3 是**持续增长的已知故障模式库**——试点与后续切片中每遇到一个新的、可复现的异常模式，必须在切片收尾时**追加一行**（症状 / 处置），否则视为文档回写不完整（可由 §6.3 的 G2/G5 检出）。

## 10. 授权、Git 与发布纪律

### 10.1 授权

- `git commit` / `git push` **必须**同一轮显式授权；**不得**因"收尾顺手"而提交。
- 授权范围严格按用户措辞：只授权提交就不推送；只授权 origin 就不碰 gitee。

### 10.2 推送

- **只推 `origin`**；**gitee 仅镜像，未经同轮显式要求禁止任何 gitee push**。
- 授权后推送并**观察 CI**（§6.4）。

### 10.3 暂存

- 用 `git add <具体文件>` 精确暂存；**禁止 `git add -A`**。
- 提交信息风格 `<type>: <summary>`（chore/feat/fix/docs/test/build），双语提交信息用英文。

### 10.4 停点

流水线跑完 ⑨ 后**停在⑩**：输出切片报告与状态表，等待用户授权提交。**不得**自行 commit/push/publish。

### 11.2 回写口径

切片收尾必须回写：验证报告（新建或追加）、`DEV_PLAN{,_EN}` 段落、切片台账（状态行 / 勾选项 / 完成记录）、ADR 行（如涉及裁决）。回写内容必须**取自切片自身证据**，不得凭记忆；缺失字段标注"历史缺失"。

### 11.3 报告结构

变更概要 → 执行流水线（步骤/角色/状态/耗时/返工次数）→ 异常与兜底记录 → 环境与档位 → 审查结论摘要（⑤⑥⑦）→ **审查输入包摘要（含盲审隔离证明：首轮是否附清单、输入是否已消毒）** → 可证伪性（机械检查 + 变异检验）→ 门禁结果 → 成本与计量（各类调用次数、探针额度）→ 明确未执行事项 → 下一步建议（含各角色档位建议）。
