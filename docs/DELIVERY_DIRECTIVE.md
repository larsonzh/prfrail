## 0. 准则的地位、版本与变更

### 0.1 权威关系

| 主题 | 权威文档 |
|---|---|
| 产品需求、验收标准 | `docs/PRODUCT_REQUIREMENTS{,_EN}.md`；切片级验收台账见『切片台账』行 |
| 协议与语义（wire / 状态机 / 门禁语义） | `docs/CONTRACTS.md`（+ `_EN`）、`schemas/`、契约夹具 |
| 实施计划与里程碑 | `docs/DEV_PLAN.md`（+ `_EN`） |
| 证据与结论 | `docs/validation/`、`docs/validation/evidence/` |
| **交付执行纪律（本准则）** | **`docs/DELIVERY_DIRECTIVE.md`（+ `_EN`）** |
| 编码/行尾/Git 纪律 | `docs/CODING_CONVENTIONS.md`、`.github/copilot-instructions.md` |
| 切片台账与剩余切片 | `docs/t027/REMAINING_SLICES{,_EN}.md` |
| 架构决策记录（ADR） | `docs/ADR_REGISTER{,_EN}.md` |
| 门禁判据实现与真值源 | `tools/gates/**`（判据文本见 §6.3） |
| 角色集（载体定义） | `.github/agents/*.agent.md`（规则见 §2.5 / §2.6） |

**冲突处理**：执行纪律冲突以本准则为准；协议语义冲突以 CONTRACTS 为准。两者冲突时**先修订文档再执行**，不得在执行中二选一。

**类别判定标准**：涉及 wire 格式、状态转移、门禁判据、证据字段的 = **协议语义**（以 CONTRACTS 为准）；涉及流程、角色、授权、文档形式、报告结构的 = **执行纪律**（以本准则为准）。仍不能判定者，**以 CONTRACTS 为准**（保守原则）。

**术语消歧**：本节『门禁判据』指 CONTRACTS 定义的**运行时 gate**（步内 gate / postflight / freeze）；§6.3 的 G1–G7 **交付自检判据**属**执行纪律**，以本准则为准。

### 0.2 版本与变更

- 版本号 `vMAJOR.MINOR`；`MAJOR` = 角色集或流水线结构的变更；`MINOR` = 规则增补。
- 每次变更必须：① 更新版本号与日期；② 在 §0.3 追加变更日志（含『受影响的在飞切片』列）；③ 在该列填写：切片 ID + 影响性质（阻塞 / 需回写 / 无需动作）；历史缺失者标注『历史缺失』。
- **本准则自身也是被验证对象**（见 §12）：不得宣称"已验证有效"，直至 §12.2 的试点通过。

**裁决注记（2026-09-23，v1.12）**：v1.7（角色文件 `model` 删除与标识消歧）、v1.9（§1.6 三档启动）、v1.11（§5.1 ⑧c 环节）按本节现行定义应属 MAJOR（角色集 / 流水线结构变更），当时按 MINOR 发布。本注记承认该事实、不追溯改写历史版本号；**自 v2.0 起严格执行**本节的 MAJOR/MINOR 定义。

## 1. 适用范围与切片模型

### 1.1 适用范围

- 适用：ProofRail 仓库内**一切需要交付产物的工程活动**（代码、契约、schema、fixtures、脚本、文档、证据包）。
- 不适用：纯咨询式问答；单条命令的临时排查（此类无需切片、无需审查，但不得产生仓库改动）。
- 工作分级（`[ROUTINE]` / `[SLICE]` / `[PILOT]`）与各级的流程、审查层、留痕与成本见 **§1.6**；本节的“不适用”项**不产生仓库改动**，与 §1.6 的 `[ROUTINE]` 档**不是同一类**（差异见 §1.6「`[ROUTINE]` 适用」段）。

### 1.2 切片（Slice）

**切片 = 最小可审查交付单元**。每个切片必须有一份**切片定义**，含：

| 字段 | 要求 |
|---|---|
| 标识 | `A0`/`B3c`/`DR-2` 式的稳定编号 |
| 目标 | 一句话，可判真假 |
| 依赖 | 前置切片或外部授权 |
| 规模 | S / M / M-L / L |
| 步骤 | 可勾选清单 |
| 现状缺口 | 为什么现在不做会出问题 |
| 交付物 | 文件级清单 |
| 验收证据 | 可机械核验的断言 |
| 边界 | **明确不做**什么（防扩范围） |
| 分级 | [ROUTINE] / [SLICE] / [PILOT]（见 §1.6；无触发词默认 [ROUTINE]） |
| 探针额度 | 需要真实外部调用时的上限声明（§7.6）；无需则写「无」 |
| 执行自由度清单落盘路径 | 见 §1.7.3 留痕要求（固定路径） |

### 1.3 一次一片

同一时刻**只允许一个切片处于“进行中”**。

**并行口径（硬规则 R1.1）**：并行**只允许出现在主控自身的工具调用层**（例如同一条消息内发多条只读命令）；**不得并行调用多个子代理**（`runSubagent` 是串行阻塞的，见 R5.1）。跨切片并行仅在用户显式授权时允许，且**只读**；**不得**并行跑会互相干扰的实机实验（进程 / Job Object / 端口 / 临时目录），见 §四.11 原件（附录 A）。

### 1.4 协议先行（硬规则）

凡语义变化，顺序固定：**CONTRACTS 双语 → schema / fixtures → 代码 → 聚焦测试 → 文档回写**。不得让代码先行。

### 1.5 工作区卫生

- 开工前工作区必须干净；未提交的历史改动必须先由用户处置（提交 / 暂存 / 丢弃）。
- 临时产物只放仓库根 `tmp/`（gitignored），**用完立即清除**，不得跨切片遗留。
- 不得在切片运行期间并行跑会互相干扰的实机实验（进程 / Job Object / 端口 / 临时目录）。

### 1.6 工作分级与启动授权

**本准则仅此一处定义触发词语法，其余小节只引用 §1.6。**

**三个级别**（无触发词即默认 `[ROUTINE]`）：

| 级别 | 触发 | 流程 | 审查层 | 成本 |
|---|---|---|---|---|
| 日常 `[ROUTINE]` | 无触发词（默认） | 主控**亲自**执行 + §6.1 基础门禁 + §6.3 自检；**不走 §5.1 流水线、不派任何子代理** | ⑤⑥⑦ **全豁免** | **0 次付费调用** |
| 切片 `[SLICE]` | 见下方触发词语法 | 按 §5.1 走流水线；角色按 §5.2 矩阵裁剪 | 按 §5.2 | 按 §7.5 |
| 试点 `[PILOT]` | 见下方触发词语法 | 同切片，**外加** §12.1 的量化指标声明 | 同切片（按 §5.2） | 同切片（按 §7.5） |

`[ROUTINE]` 适用：对话式协作、小改动、出方案；**可产生仓库改动**（落盘与授权按 §10，与 §1.1 的“不适用”项不同）。**与 §1.1『不适用』的可判分界 = 是否落盘**：将产生仓库改动（落盘）⇒ `[ROUTINE]`；不产生任何仓库改动（纯咨询 / 临时排查）⇒ §1.1『不适用』。

**触发词语法**：

- 形态：`切片：<id> <描述>` / `SLICE:<id> <描述>` / `试点：<id> <描述>` / `PILOT:<id> <描述>`。
- 位置：必须出现在**消息首行前 20 个字符以内**才生效（防正文提及触发词被误判）。
- **计数单位**：「前 20 个字符」按 **Unicode 码点**计；计算前**跳过**行首空白与 `>` 引用符；触发词的**首字符**必须落在该 20 码点窗口内。
- **`[id]` 字符集**：字母、数字、`-`、`_`、`.`（1–32 字符，不含空白与全角标点）；含空白的历史 ID（如 `B4 · AT-23`）在触发词中改写为 `-` 或 `.`，台账显示形式不变。
- 全角 / 半角冒号均可；英文形态**大小写不敏感**。
- **日常档不设触发词。**
- 若触发词出现在**首行前 20 字符之外**（例如正文中提及），**不生效**；主控按 `[ROUTINE]` 判定，但**必须**在回执中显式标注“**检测到疑似触发词但位置不合法**”并建议用户重发。
- 若**首行前 20 字符内命中多个触发词**（含同一形态出现两次或两条不同 ID），**不生效**；主控须**停下并要求用户重发**，不得自行择一，**也不得按 `[ROUTINE]` 继续执行**。

**日常档的不可绕过边界**（触及即必须建议升级，**不得继续执行**）：

- ① **§7.2.1 ③ 所列的全部语义类别**（状态机 / 门禁判据 / 证据模型 / 角色 / 授权契约）。**本项为引用，不重复定义。**
- ②–⑥ 为本档**增量**边界：CONTRACTS / schema / fixtures 的语义；任何 `.agent.md`；涉及状态机、崩溃路径、所有权、并发的代码（**该项以生产代码边界为准，列此仅为对照**）；`.github/workflows/**`；**新增 / 删除 / 升级 / 降级依赖（含锁文件变化）**。
- **另（生产代码语义边界，2026-09-23 用户裁决）**：生产代码（`.go`）的**任何语义改动**——新增 / 修改 / 重构 / 错误处理 / 分支 / 返回值——**必须走 `[SLICE]`**；纯注释、纯格式、文档字符串等**不改行为**的改动仍可 `[ROUTINE]`。

> **适用关系口径（2026-09-23）**：§5.2 与 R5.3 的『⑦ 不可省』只约束 §5.1 流水线内的切片；§1.6 的『⑤⑥⑦ 全豁免』只适用于 `[ROUTINE]` 档（不走 §5.1 流水线）。二者作用域互斥、不冲突——一旦进入 `[SLICE]` / `[PILOT]`，⑤⑥⑦ 按 §5.2 启用、⑦ 不可省。

> **越权指令的处理**：若用户明示“按日常档完成”，主控**必须拒绝**并给出理由；用户坚持时，主控须以**书面形式记录“用户越权指令”**，再按下列降级执行：**只做不触及边界的最小部分**，剩余部分明确列入“**未完成清单**”并说明需按 `[SLICE]` 重跑。

**主控的判定与建议义务**：

- 收到消息后**先判定级别**，并在**回执首行**声明 `[ROUTINE]` / `[SLICE]` / `[PILOT]` ＋ 一句理由。
- **可建议、不擅自升级**：发现比预期大 ⇒ 回一句建议升级并**停下**等用户明说；用户不升级 ⇒ 只允许改做边界外部分或完全停下，**不得**以“小范围”名义继续触碰边界内容。
- **级别单向**：进入 `[SLICE]` / `[PILOT]` 后**不得半途降级**；若用户明确要求降级，**停止当前切片**并以 `[ROUTINE]` **重新开始**，不得在原切片内切换；`[ROUTINE]` 发现变大 ⇒ 建议升级。
  - **停止态的工件标记**：已产出工件**保留原位**，但**不得作为已完成切片提交**；其报告头部必须标 `**状态：已停止——未完成**`，并列“**未完成清单**”。
  - **停止态不视为闭环**：不得在台账 / `DEV_PLAN` 中按“完成”处理；`REMAINING_SLICES` 该行保持 `🔄` 或改回 `⬜`（**由用户裁决**）。§11.2 的回写义务针对“切片收尾”，**不适用**于停止态。
  - **重启路径**：以 `[ROUTINE]` 重新开始时**视为新工作**；停止记录**保留在原切片报告中**，作为“为何降至日常档”的上下文。
- **不因日常档豁免 §10**：`[ROUTINE]` 的改动**可积累**到一次提交，但提交 / 推送**仍须 §10 的同轮显式授权**。

**留痕与成本**：

- `[ROUTINE]`：最小留痕 = diff ＋ §6.1 门禁结果 ＋ §6.3 自检结果；**§6.3 自检全量适用**（不得因日常档豁免）；**0 次付费调用**。
- `[SLICE]` / `[PILOT]`：留痕按 §5.3 与 §11，成本按 §7.5。

> **消歧（两个不同维度）**：工作分级（`[ROUTINE]` / `[SLICE]` / `[PILOT]`）与 **§8.2 的思考档位（low / high / max）** 是**两个不同维度**，不得混用——前者决定流程与审查层，后者由 operator 在启动前一次性设定；级别声明不代替 §8.2 的档位设定，档位设定也不代替本节的级别判定。另：`[ROUTINE]` 档的档位口径见 §8.2 的 `[ROUTINE]` 行。

### 1.7 执行自由度与升级边界

**1.7.1 执行自由度（可自主）**：下列事项主控或产品层角色**可自行决定**，无需停下问用户：

- 单文件实现选择；
- 契约已明确范围内的实现方式；
- 已授权包内的门禁重试；
- 不影响契约语义的重构；
- 契约措辞的补全。

**1.7.2 升级边界（必须停下问用户）**：触及下列任一项，**必须停下**并向用户确认，不得以执行自由度为名继续：

- 涉及契约语义的任何变更；
- 超出切片范围的顺手修；
- 预算额度耗尽；
- 判定“这是扩范围还是执行自由度”有歧义时；
- §1.6 的不可绕过边界。

**§1.6 的不可绕过边界优先于 §1.7.1 的执行自由度**——凡触及 §1.6 边界的事项，一律按升级边界处理，不得以 §1.7.1 为准。

**1.7.3 区分原则**：“怎么做”可自主，“做什么”永远属于用户。判定方法（三支）：**这个决定如果错了，需要修改的是什么？**——错了要改**代码** ⇒ 属执行自由度；错了要改**契约 / 方向 / 范围 / 预算 / 授权**（即 §1.7.2 所列各项）⇒ 属升级边界。清单未覆盖者按 §1.7.2 末项（有歧义即停下）处理。

**留痕要求**：主控行使执行自由度时**不逐条报告**，但切片验证报告的“变更概要”节**必须**列出行使自由度做出的实质性选择。**产出与落点**：该清单由**主控**在 ⑥ 之后、⑦ 之前作为**编排工件**落盘至固定路径 `docs/validation/evidence/[切片ID]-freedom-list.md`；⑧b 定稿再将该清单回写进验证报告，二者内容必须一致；⑦ 终审复核其**审查输入包中的同一清单**（清单在 ⑦ 之前产出，与 §5.1 时序相容），并据此判定是否越界。**覆盖边界**：该路径位于 `docs/validation/evidence/**`（G7 的扫描域之外）⇒ 该清单**无机械判据保护**，只由 ⑦ 人工复核（同 §6.3 G7 的排除口径）。

## 3. 主控职责与边界

### 3.1 主控做什么

1. **任务分解与派单**：把切片拆成原子工作包，为每个包写明：输入材料、期望输出、验收条件、**模型串**。
2. **上下文最小化投喂**：只给子代理完成任务所必需的材料；凡涉及审查方，一律给**证据路径**而非转述（§6.2）。
3. **门禁执行**：在关键节点亲自运行 build / vet / 聚焦测试 / 编码门禁 / 收尾自检（§6）。
4. **审查调度**：按 ⑤→⑥→⑦ 顺序调度，按结论决定通过或打回；执行闭环纪律（§5.3）。
5. **证据管理**：把 diff、门禁输出、探针结果落盘并交付路径（§6.2）。
6. **兜底**：见 §9。
7. **停点**：§10.4。

### 3.2 主控不做什么（硬边界）

- **不原创产品工件**：不写生产代码、测试代码、CONTRACTS/schema/fixtures、验证报告正文。定位到问题后**指派对应子代理**修复。
- **不代替审查方下结论**：不得自行判定"预审/扫描/终审通过"。
- **例外（编排工件，允许且必须由主控产出）**：任务包、状态表、证据文件（diff/日志落盘）、异常与兜底记录、报告**装配**（把子代理产出与门禁结果汇总成报告，不改写其结论）、台账与状态标记回写。
- **机械集成豁免**：把子代理产出的补丁落到文件属**机械集成**，不算"写代码"，但必须过三重校验：① 落盘前后 diff 行数一致；② 涉及 `.md` 时编码门禁通过；③ 落盘后立刻跑聚焦门禁。
- **例外扩展（准则治理切片，2026-09-23 用户裁定）**：**附录 C 条目**的验证报告由主控直接产出，属**编排工件例外**；① **仅限**附录 C 条目（其他切片的验证报告仍按本节原规则执行）；② **不豁免** ⑤⑥⑦ 审查；③ **不改**其他切片的规则。

### 3.3 主控的自检义务

主控必须对**自己的每一轮改动**跑 §6.3 的收尾自检；发现不一致**当场修**或指派子代理修，不得留给用户或审查方发现。

### 3.4 编辑后诊断扫描（硬步骤）

**任何一次编辑后、进入下一步之前**，主控必须对本次编辑按下列类别运行诊断扫描；本步骤与 §3.3 的自检并列，**不可跳过**。

**3.4.1 工具选用（按语言 / 文件类别，不枚举扩展名）**：

- 编译型（Go 等）：`go build ./...` + `go vet ./...`；
- 脚本语言：该语言的语法检查 / 静态分析器；
- 标记数据（`.md` / `.json` / schema）：编码门禁（§6.1 编码行）＋结构解析器；
- 纯文本其他：编码门禁；
- 未覆盖类型：**兜底**——编码门禁 ＋ 人工可读性检查。

**3.4.2 硬性约束**：任何新增告警**不得遗留到下一步**——必须就地修复或指派子代理修复，修复后重跑诊断至无新增告警。“未覆盖类型”**不是“免检”**：仍需通过编码门禁 ＋ 人工可读性检查。

**3.4.3 工具化优先**：优先在 `tools/gates/` 实现“诊断聚合器”（单一入口，按 §3.4.1 的类别表聚合各语言诊断输出）。

**3.4.4 与编码层的关系**：§6.3 G4（编码 + 异常字）与 §6.1 编码行覆盖**编码层**；本节覆盖**语义层**（诊断告警的生成、聚合与清零），二者互补、不互相替代。

**3.4.5 依据**：2026-09-23 用户观察——Flash 改动代码后经常遗留报警；根因是缺少“编辑后诊断”的固定步骤，**不是档位**。

3. 主控判定切片类型并**设定档位**（§8.2；一经设定，连续运行中不切换）。
4. 生成**任务包**（每包含：输入材料、期望输出、验收条件、`modelId` 串），随后进入 ①。
5. 任一项不满足 ⇒ **标记“依赖阻塞”并停下**，不得自行推断或降级执行。

> **入口模板**：用户起跑消息、主控开场回执、停点回执与“最小阅读集”见 **附录 B.7（启动卡）**（其硬约束见 B.7 首段）。

### 5.1 流水线

```
①架构（如需） → ②实现 → ③测试 → ④主控集成+门禁 → ⑤预审(V4 Pro)
```

**说明：⑧ 分两步（防文档滞后）**——**⑧a 初稿**在 ⑦ 之后立即做（不阻塞 ⑨，先把已定结论落盘）；**⑧b 定稿**在 ⑨ 之后做，吸收原生验证结果与任何回退修复。⇒ 避免“⑨ 失败导致文档重写”。

## 6. 门禁与证据

### 6.1 基础门禁（每次改动后）

| 门禁 | 命令 / 判据 |
|---|---|
| 格式 | `gofmt -l .` 输出为空 |
| 构建 | `go build ./...` exit 0 |
| 静态检查 | `go vet ./...` exit 0 |
| 单元测试 | `go test ./...` exit 0（记录 ok 包数与 FAIL 计数） |
| 契约夹具 | 涉及契约时补跑 Node 合同检查（夹具计数必须同步） |
| 编码 | `.md`/`.ps1` = UTF-8 **with BOM** + LF；`.json`/`.go` 等 = **without BOM** + LF |

**聚焦门禁定义（2026-09-23）**：`聚焦门禁 = go test ./[受影响包]/... -run [测试点前缀]`（或等价的契约夹具子集）；切片定义的『步骤』字段**必须写明该命令**。

### 6.2 证据落盘义务（硬规则 R6.1）

**所有审查类子代理都没有 `execute` 能力**（实测：`deep-reasoner`、`independent-reviewer` 仅 `read`+`search`）。因此：

- 审查前，主控必须把**原始 diff** 与**门禁原始输出**落盘（仓库根 `tmp/` 下，用完清理；路径规则见 §1.5），并把**路径**交给审查方。
- **禁止**只把 diff 摘要/转述贴进 prompt 就当"已提供证据"。
- 先例：B3c ⑦ 复审曾因"未提供原始 hunk"整轮作废；改为落盘 `tmp/b3c-review.diff` 后一次通过。

### 6.3 收尾自检门禁（七类机械检查，**强制**）

**位置**：`tools/gates/`（纳入版本控制）。**触发**：任何切片收尾前、任何 docs-only 提交前。
**原则**：把"人肉记忆"换成"机械断言"——本准则不假设任何角色不会忘事。

| # | 检查 | 判据 |
|---|---|---|
| G1 | **状态标记一致性** | 小节标题的状态符号 ↔ 状态表行 ↔ 完成记录行，三处必须一致（如 B3c 曾出现标题仍 `⬜` 而状态表已 ✅）。**豁免（2026-09-23）**：停止态切片（§1.6）不参与本判据的三处一致性判定，按 §1.6 的停止态标记规则执行（报告头标『已停止——未完成』、台账保持 🔄 或改回 ⬜）；其完整性由 G7-d 负责。 |
| G2 | **占位符残留** | 全文不得残留"待…回填""尚未提交""待同轮授权""pending the push"等占位（切换后这类必须已被事实替换）。**扫描范围必须排除本行自身的规则引文**——否则本行引用的被禁字符串会被自己判为违规（**自指缺陷**，2026-09-21 实测：§6.3 自扫得 4 条假阳性）；实现上按"引号内被禁串 + 所在行含『不得残留』⇒ 跳过"处理 |
| G3 | **双语对称** | (a) **改动行数对称**：对每个被改动的 CN/EN 文档对，`git diff --numstat` 的 新增/删除 行数必须相等（2026-09-21 实测：本片 6 对全 PASS）。**不要求**全文行数或加粗标记数相等——既有双语对历史就不对称（`REMAINING_SLICES` 501/488、`B2-EXTERNAL-ENFORCEMENT` 270/315），“全文相等”对它们不可满足（**自指缺陷**，同 G4b）。(b) **关键字段对齐（作用域 = 变更行，非全文）**：`git diff -U0` 的**新增行**中，CN/EN 两侧的**提交号 / run 号 / 状态枚举 / 结论枚举**计数必须相等——行数对称**不能**证明语义未漂移（⑦ 首轮 Medium 发现）。**不得**用全文比对：全文差异可能来自历史遗留（实测：`B2-EXTERNAL-ENFORCEMENT` 全文 10/9，而变更行 0/0）。 |

## 7. 审查体系

### 7.1 三层审查

| 层 | 角色 | 定位 | 关键要求 |
|---|---|---|---|
| ⑤ | 预审员（V4 Pro） | 实现是否偏离方案 | 覆盖方案书逐条 + 反例三类 |
| ⑥ | 独立扫描（MAI） | 低成本补充扫描 | **不参考任何他人清单**；Section A–E |
| ⑦ | 独立终审（Codex） | 唯一终审门禁 | **首轮不附任何 ⑤/⑥ 清单**；四项审查 |

> **说明（⑧c 不属于三层审查）**：⑧c 收尾清洁由**主控执行**，**不属于**⑤⑥⑦ 三层审查——它是 §5.1 的固定环节（见 §5.1 / §3.4），与 ⑨ 原生验证并列。

### 7.2 ⑥（独立扫描层）

### 7.2.1 触发

**触发**：
- **行为变更切片**（改契约 / 状态机 / 崩溃路径 / 进程治理 / 所有权语义）→ **启用**；
- **可跳过**仅当下列三条**同时**满足：① 改动**只落文档与配置文案类文件**（`.md`/注释/文案；`.gitignore`、`.txt`、`.html` 等非机器结构文件计入此类）；② 不含 `.go`/`.json`/`.yml`/schema/fixtures/**脚本逻辑**的语义变更；③ **不涉及状态机、门禁判据、证据模型、角色/授权契约的语义**。**跳过必须由 ⑦ 或用户确认**（主控不得单独认定“可跳过”），并在报告中记录理由。
    - **反面样例（2026-09-21 实测，不得重犯）**：SW-1/SW-2 表面是“文档切片”，但它**修订了 §6.3 门禁判据与证据模型** ⇒ **③ 不成立，不得跳过 ⑥**。主控最初的跳过理由**不成立**，经 ⑦ 第 2 轮指出后**已补跑 ⑥**（结果见验证报告 §7.2b）。⇒ 判定“可跳过”必须**逐条核对 ①②③**，不得按“看起来是文档”推断。

### 7.2.2 ⑥ 层的输出契约与成本上限 / 失败处置

**⑥ 输出契约（Section A–E，与 ⑦ 的契约同构）**：

- **Section A**：总体结论行 —— `INDEPENDENT SCAN: PASS` 或 `INDEPENDENT SCAN: FINDINGS`。
- **Section B**：发现清单，每行固定格式 `SEVERITY | file:line | 被违反的句子（逐字引用） | 最小修复`。
- **Section C**：逐条证据与推理。
- **Section D**：**可证伪性审计（硬性）** —— 逐项给出“若删掉某守卫，哪个检查/断言会红、哪个不会红”，并列出它认为**没有覆盖**的不变量。
- **Section E**：**“我无法验证的部分” + “什么会推翻我的 PASS”**（防橡皮图章）。

> **继承来源与唯一权威**：A–E 定义取自 v3.1 §2.2（原文见 `docs/t027/FLASH_OPERATING_DIRECTIVE_v3.1.md`）。本准则 §4.2 / §7.2 / 附录 B.6 三处对 `Section A–E` 的引用**以本定义为唯一权威**（2026-09-21 补齐：此前三处引用而**无定义**，属**引用断裂**）。

**成本上限**：单片 MAI 有效调用（含首轮、重发、整改重跑）≤ **3** 次；重发仅限"截断/异常"且计入上限；Haiku 另计 ≤1。
**失败处置**：MAI 报 Medium+ ⇒ 修复后**重跑 MAI**；若 MAI 输出**格式偏离**（未按 Section A–E / 无结论行）⇒ 允许重发 1 次；**再偏离或达上限 ⇒ 该层不得宣告通过**：必须 ① 如实留痕并记录“⑥ 未产出可执行发现”；② **进入 ⑦ 独立终审并按 ⑦ 的结论闭环**；③ 必要时升级用户裁决；随后仍可并由 ⑨ 追加"专项独立佐证实验"承担 A12 角色。**该层结论不构成审查充分性证明。**

### 7.2.3 Haiku 启用前置条件

必须**先确认后启用**：① Copilot 模型列表中存在 `Claude Haiku 4.5`；② 访问通道（代理/网络出口）正常并以首个真实调用完成可用性预检。任一不满足 ⇒ **按三级回退处置**：① 退回 ⑤ 请 V4 Pro 补扫一轮（预审加一轮）；② 若 ⑤ 已收口，则**跳过 ⑥ 并在报告中记录理由**，由 ⑦ 承担独立扫描职责；③ 若 ⑦ 亦无法覆盖，则**升级用户裁决**；**不得反复重试**，也不得把其缺席计作 ⑥ 失败。

### 7.3 输入消毒与结论落地

- **输入消毒**：交审查方的材料必须过滤 IP、用户名、主机名、SSH 路径、凭据、token。
- **结论落地校验**：审查方给出的每条 `file:line` 必须在落地前**逐条复核**是否真实存在且与判据一致；无法定位者按"线索"处理，不得直接采信。
- **锚定硬隔离**：⑦ 首轮只给切片定义、diff、契约原句、只读约束；仅**复审轮**可附清单，并标注"完成独立扫描后再读"。

### 7.4 一次做对（减少 ⑦ 打回）

实现前必须：① 方案书的改动点精确到文件；② 测试点可执行且含反例；③ 契约先行已完成；④ 门禁本地全绿。**打回成本远高于前置澄清成本。**

### 7.5 成本上限（硬指标）

| 角色 | 单片上限 | 备注 |
|---|---|---|
| 架构师 | ≤ 1 | 复杂/高风险切片 |
| 预审员 | ≤ 1（整改后复审 +1） | 不含 ⑦ 的盲审叠加 |
| ⑥ MAI | ≤ 3（有效调用） | 见 §7.2 |
| ⑦ Codex | 1（终审）+ 1（复审） | 整改后必须复审属义务；"盲审必抽"另计 +1，可与后者合并但**必须在启动前判定并记录理由**；**例外与停止判定见 §7.8** |

超出上限 ⇒ 升级到用户裁决。**成本梯度提示**（实测定价，USD/百万 token，offPeak 输入/输出）：Flash `0.15/0.6`、V4 Pro `0.66/1.98` ⇒ **优先把编码/测试/文档/门禁下沉到 Flash**。

**硬规则 R7.1（计量真值源与去重）**：上表计数只能取自**单一真值源**——**会话调用回执/日志**（不得用“我估摸用了几次”）。每条调用必须可识别 `{role, model, stage, startedAt, reason, retryOf}`；**去重规则**：同 `stage` 的**重发**（截断/异常）**计入上限**；**整改后的复审**单独行计数；**盲审**与终审分列。报告“成本与计量”必须按本字段逐项列出；来自会话日志之外的口述计数**不作数**。

### 7.6 预授权探针额度

需要真实外部调用的切片必须预先声明额度上限；额度用尽即停，**不得**在切片中追加。探针使用必须记账（次数、付费数、结论）。

### 7.7 残差治理（A11 / A12）

- **A11 对称抽查**：主控从 ⑥ 与 ⑦ 的"删掉守卫 X ⇒ 测试 Y 变红"声明中**各随机抽 1–2 条实际执行**；声明与实际不符 ⇒ 该审计可信度降级，记为负向信号。抽查只提供**存在性佐证**，不构成覆盖率证明。
- **A12 独立佐证**：⑥ 报 PASS 时，⑨ 必须至少有一项**专项实验**独立证明关键不变量（与 ⑥ 无关的判据）。
- **必抽盲审**：切片触及**所有权 / 停机 / 身份**语义时，⑦ 之前追加 **1 次盲审**（不附任何清单）。其调用计数与“是否与 §7.2 兜底合并”的口径**统一由 §7.5 规定**，本节不另行累计，避免两处叠算。
    - **按比例抽查（承接 v3.1 §3.11）**：除“必抽”外，**每 4 片抽 1 片**做一次 ⑦ 盲审（从最近 4 片中选触及面最广者）；抽样记录（片号 / 盲审发现数 / 是否推翻 ⑥ 的 PASS）写入报告。

### 7.8 评审收敛判据（何时可以停止）

## 8. 档位（思考模式）规则

### 8.1 基本事实（实测）

- 档位是 **API 层参数**；模型**无法感知、确认或自改**档位，子代理自报档位亦不可信（实测 `effort=unknown`）。
- 档位由 **operator 在开跑前设定**；**连续运行中无法动态改变**。
- `deepseek-flash`（主控与产品层同用）支持 `low / high / max`，默认 `high`。

### 8.2 档位设定（按切片类型，**启动前一次性设定**）

| 切片类型 | 主控 | 架构师/预审员 | 产品层（实现/测试/文档） | ⑥ / ⑦ |
|---|---|---|---|---|
| 简单 | High | — | 与主控同档（见 §8.3） | 各自的模型默认/固定档 |
| 中等 | High | Max | 同上 | 同上 |
| 复杂 | High | Max | 同上 | 同上 |
| 高风险 | **Max** | Max | 同上 | 同上 |
| 日常 [ROUTINE] | 沿用当前会话档位（不按本表设定） | — | — | — |
| ⑦ Codex | — | — | — | **Extra High（固定）** |

### 8.3 同模型角色的档位不可分离（**已知限制**，D2=A）

主控与产品层**同为 `deepseek-flash`** ⇒ 二者的档位是**同一个设置**，无法在连续运行中分别为"主控 High / 实现者 Low"。

- **接受同档**：默认整体取 **High**。
- **需要 Max 时**：① 在**任务启动前**把 Flash 档位配为 Max；或 ② 任务进行中**暂停 → 改档 → 继续**（暂停前后必须重跑一次门禁确认状态）。
- **长期解**：为产品层配置**不同的模型**（按角色配模型），届时本限制解除。

### 8.4 档位变更的记录义务

每次改档必须在报告"环境与档位"表中记录：设定时刻、档位值、是否经过暂停、暂停前后门禁结果。

## 9. 主控兜底与异常处理

### 9.1 兜底触发场景

| 场景 | 主控行动 |

| 子代理输出为空 / 明显不合理 | 重新裁剪上下文后**重试 1 次**；仍失败 ⇒ 记异常，换备用载体或降级工序 |
| 子代理连续 2 次失败 | 暂停该环，输出诊断报告，**标记需人工介入**。**例外**：⑥ 独立扫描层的重发按 §7.2 成本上限（≤ 3 次有效调用）执行，达到上限后才计入本条的连续失败计数 |
| ⑤/⑥/⑦ 结论互相矛盾 | 主控**根因仲裁**：复现最小反例 → 判定谁错 → 决定修复路径 → 写入报告 |
| 门禁异常且非代码问题 | 检查环境/依赖/配置；必要时重建环境（不得改动生产代码掩盖） |
| 边界模糊 / 依赖未满足 | 向上回溯切片定义，**标记"依赖阻塞"并停下**，不得自行推断 |
| 原生验证失败且原因不明 | 逐层剥离定位根因 → 指派对应子代理修复 |

### 9.2 兜底原则

1. **兜底不等于代写**：定位问题后仍指派产品层角色修复；主控只做机械集成与门禁。
2. **每次兜底必须记入报告"异常处理"章节**（场景、定位过程、指派路径、结果）。
3. **阈值合并**：同一切片兜底介入 **> 3 次** ⇒ 自动标记"高风险切片"并**暂停等人工审核**；与 §5.3 的"⑨ 连续 2 次失败升级 ⑤"**共用同一计数**，不得形成两套并行阶梯。**计数口径（2026-09-23）**：『兜底计数』= 主控为定位 / 修复 / 重跑而介入的**逐次行动**；同一环同一根因的修复重跑计 1 次。

### 9.3 已知异常模式（先验清单，供快速定位）

| 模式 | 症状 | 处置 |
|---|---|---|
| SCM 陈旧显示 | 编辑器显示"未跟踪"但 git 干净 | 以 `git status --porcelain -uall` 等四条命令为准；刷新/重启编辑器 |

| 工具匹配宽松 | 替换工具对形近 oldString 仍报成功 | 改后必跑机械断言，不信任"success"回显 |
| 编码默认值 | 新建 `.md` 无 BOM / CRLF | 落盘后立即跑编码门禁并纠正 |

| **封版后追加 ⇒ 判据作用域退化** | 对已提交版本追加「封版裁定 / CI 结果」类记录时，暂存集不含原切片的提交 ⇒ ⑨ 与 G6 的变更行作用域从整片变更集**退化为本次追加**；空变更集时甚至无行可判 | 追加记录的读数**必须与其被记录时的提交绑定**（把读数文件与提交号同档落 `tmp/`，报告写明口径）；本体已封版则**不改**本体，本轮读数另存——OB-41 落地，见 §6.3 的 G6 作用域 |

## 10. 授权、Git 与发布纪律

### 10.1 授权

- `git commit` / `git push` **必须**同一轮显式授权；**不得**因"收尾顺手"而提交。
- 授权范围严格按用户措辞：只授权提交就不推送；只授权 origin 就不碰 gitee。

### 10.2 推送

- **只推 `origin`**；**gitee 仅镜像，未经同轮显式要求禁止任何 gitee push**。
- 授权后推送并**观察 CI**（§6.4）。

### 10.3 暂存

- 用 `git add <具体文件>` 精确暂存；**禁止 `git add -A`**。
- 提交信息风格 `<type>: <summary>`（chore/feat/fix/docs/test/build），双语提交信息用英文。

### 10.4 停点

流水线跑完 ⑨ 后**停在⑩**：输出切片报告与状态表，等待用户授权提交。**不得**自行 commit/push/publish。

## 11. 文档与台账

### 11.1 权威分域与双语

- 权威分域见 §0.1；中文为权威、`_EN` 为镜像；镜像必须**逐句对齐**（不只关键词）。
- 历史版本（如 v3.1 准则、已冻结的验证报告）**不重写**，只加指针或更正注记。

### 11.2 回写口径

切片收尾必须回写：验证报告（新建或追加）、`DEV_PLAN{,_EN}` 段落、切片台账（状态行 / 勾选项 / 完成记录）、ADR 行（如涉及裁决）。回写内容必须**取自切片自身证据**，不得凭记忆；缺失字段标注"历史缺失"。

### 11.3 报告结构

变更概要 → 执行流水线（步骤/角色/状态/耗时/返工次数）→ 异常与兜底记录 → 环境与档位 → 审查结论摘要（⑤⑥⑦）→ **审查输入包摘要（含盲审隔离证明：首轮是否附清单、输入是否已消毒）** → 可证伪性（机械检查 + 变异检验）→ 门禁结果 → ⑧c 收尾清洁记录（§5.1）→ 成本与计量（各类调用次数、探针额度）→ 明确未执行事项 → 下一步建议（含各角色档位建议）。
